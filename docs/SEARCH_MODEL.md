# The search model

Search by meaning on this Mac uses one optional model, **EmbeddingGemma 2** by Google. It is never bundled and never downloaded
without a click: Settings → Models → Download (or Import from a file). This page is the reference for how it is pinned,
verified, run and ranked, and for the one third-party dependency that runs it.

User-facing summary: PRIVACY.md and README.md. Release steps: [RELEASING.md](RELEASING.md).

## Download and verification

`SearchModelDownloader` runs only after the person clicks Download, through `AuditedSession` with the purpose `modelDownload`
(Network Activity: "Search model download").

1. Resolve each file at `https://huggingface.co/google/embeddinggemma-2/resolve/914f7f8…/{model.safetensors|tokenizer.json}`
   (exact paths; nothing else is requested from that host). The answer is a 302, never followed automatically. Its `Location`
   must be `https`, port 443, no user info, and a host of the exact allowlist in `SearchModelDestinations`
   (`us.aws.cdn.hf.co`, verified 2026-10-12). Anything else is a Blocked row in Network Activity and nothing is sent.
   If the 302 carries `X-Repo-Commit`, `X-Linked-Etag` or `X-Linked-Size`, they must equal the pinned values.
2. `tokenizer.json`: one GET, capped at its pinned size, hashed as it arrives. Every request sends `Accept-Encoding: identity`, and an
   answer with another `Content-Encoding` is refused (a compressed body would have another length than the pinned one).
3. The weights: 17 HTTP Range requests of 32 MiB, each answered with exactly `206`, the exact `Content-Range`
   (`bytes a-b/1488915288`) and exactly the requested length, hashed as it arrives and compared with its pinned block hash
   before the next. A mismatch is fetched once more after resolving again; a second mismatch deletes everything.
4. All blocks in: `fsync`, then the header, each of the 413 tensors and the assembled file are verified in one pass
   (about 0.5 s with a warm page cache). Any failure deletes the partial file.
5. The signed CDN address lives in memory only; its query string never reaches the log, the export or a file. A 403 or 410 (an
   expired signature) resolves again once.

A partial download resumes from its longest verified prefix. A recording pauses it (and for two minutes after); it continues by
itself. Nothing starts at launch.

**Import** takes the original `model.safetensors`, the assembled text tower and/or `tokenizer.json` chosen by the person and
checks them with the same hashes (symbolic links are followed, as in the Hugging Face cache). Importing only one of the two files
leaves the other one to ask for: the card says "Imported the weights. Also choose tokenizer.json from the same model, or download
just the tokenizer (32 MB)" (or the reverse, with the 542 MB weights); the download then fetches only what is missing.

**Store**: `<Application Support>/Vauta Models/embeddinggemma-2/914f7f89/` (`model.safetensors`, `tokenizer.json`,
`installed.json`), next to but never inside the store directory `Vauta/`; directories 0700, files 0600, excluded from backups
(set again at every start) and from Spotlight; deleted from Settings. Erase Everything keeps it: it holds no personal data.

## Running it

`Sources/VautaMLX` is the only target that imports MLX (a test enforces it): `GemmaTextEncoder` (the model in MLX Swift,
fp16, GPU only), `SafetensorsFile` (a bounds-checked reader over a memory map), `ByteJSON` (a byte-exact parser) and
`KernelSelfTest` (59 GPU-versus-CPU checks that exercise all 9 embedded kernel groups; 17 of them cover the encoder's ops, including
  boolean-masked attention at head dimensions 256 and 512, GELU, sum and mean, the non-finite check and the bf16 casts).

- Tokenizer: pure Swift, keyed by bytes because 434 groups of vocabulary entries are canonically equivalent. 487 self-written
  strings match Hugging Face token for token (`Tests/.../tokenizer_goldens.jsonl`, checked by
  `tools/search-model/verify-tokenizer-goldens.py`); the spike matched 37,987 strings.
- `SearchModelEngine` loads on first use (full verification once per launch), batches by padded tokens (at most 1024 and 32
  rows), watches `phys_footprint` (halves the budget above 1.4 GB, restores it after 20 calm batches), retries a row that
  produced a NaN or infinity in fp32 alone, and unloads after 3 minutes idle, on memory pressure or on delete. After a memory-pressure event, bulk (document-purpose) embedding does
  not reload the model until 30 s without another event have passed, and then starts with the smallest batches; a question loads it
  at once. Deleting the model first stops the embedding job and the document pass (`searchModelRemoving`), then removes the files,
  then drops the vectors; a late report from an embedding that was suspended cannot turn the deleted model into a damaged one.
  `Memory.cacheLimit` is 128 MB (`MLXRuntime.configure()`).
- Space: `embeddinggemma-2@914f7f89/r1`, 256 dimensions (the first 256 of 768, renormalised), int8 in the existing vector index.
  Prompts: `task: search result | query: ` and `title: none | text: `. **`r1` is the recipe version**: prompts, mean pooling,
  the Matryoshka cut, the chunking rule and the tokenizer. Any change bumps it and the stored vectors are embedded again.
- Chunks must fit the 512-token sequence. Meeting chunks are planned with the tokenizer (`ChunkBudget`), so a 130-second chunk
  of Spanish, German or French is not cut. A document passage over the limit is split at sentence boundaries and embedded as the
  token-weighted mean of its windows.
- Bulk embedding waits while recording (and two minutes after), in Low Power Mode, when the Mac is hot and on battery. A
  question is embedded unless the Mac is critically hot. The one exception to "the meeting being recorded is not embedded" is
  E3 on demand (below, off by default): a question typed during a recording can embed its closed chunks at that moment, with the same battery, Low Power Mode and heat rules.

Measured on an M2 (24 GB), debug build: loaded 526 MB, 2,000 passages of 30 to 160 words peak at 1,098 MB, 174 MB after
unload; the real download took 31 s. The spike measured about 20 ms per passage in release. Not measured: Italian and
Portuguese ASR transcripts, an M5, cold-disk load.

## Ranking

The pre-meeting brief does not use the search model to rank: on its blind evaluation (8 test series, synthetic fixtures) the search model changed related meetings plus documents P@3 by -0.042 [-0.125, 0.000] against keywords, showed more irrelevant reminders and notes (+0.50 per brief [0.13, 0.88]) and its recall gain was within noise, so `BriefRankingShipping.searchModelRanks` is false. No ranking claim is made for it in the brief. See docs/BRIEF.md.

`SemanticRanker` decides, separately for meetings and documents:

| Situation | Ranking |
|---|---|
| Model not installed or not ready, or keyword search chosen | BM25 and the graph, as before |
| First indexing (coverage never complete in this space) | BM25 only; the UI says "indexing" |
| Complete coverage, or at most 50 items or 2% missing after it was reached once | **Gemma ranks**; BM25 only boosts exact matches |
| A big backlog after that | BM25 until it is under the threshold |
| Inside one meeting or a document filter | Gemma only if that scope is fully covered |
| A model server's embeddings | RRF of BM25 and vectors (k = 60), unchanged |

Gemma ranking: the candidates are the vector top 50 (400 inside a scope) plus up to 40 exact-match rows per item; the score is
the cosine from the stored int8 vector plus +0.30 when a passage contains **every** code of the question (FTS5 phrase of its
words: `PO-48213` is `"po 48213"`, so `PO-482130` does not match) plus +0.15 times the share of the question's rare names it
contains. Meetings also add +0.08 for a named entity, +0.08 for a speaker the person named and +0.04 for a noted moment; documents
add +0.04 per entity match, at most +0.08. Dates, versions and amounts (`2026-10-12`, `12/10`, `1.2.3`, `500.00`) are not codes unless a letter, `#` or `_` is in them. Names are capitalised words (or a lone word; a capitalised word that only opens a sentence counts only when it is not a
question or request word such as "What", "Qué", "Wer") that appear in at most
`max(3, rows / 20000)` rows, and never for text in scripts without spaces. A passage without a vector yet joins by its keyword
rank with the cosine of the vector hit of the same rank, so a meeting recorded minutes ago stays findable. Only chunks of the model's own
space count as covering a moment: a meeting whose chunks are still in a model server's space is found by keywords until it is
re-embedded. A moment in the one-segment overlap of two chunks belongs to both, and both are candidates and get the boost.

**Mixed scales in Ask.** Meetings and documents are ranked separately, so one can be on the cosine scale (about 0.5 to 1.4) while the
other is on the RRF scale (at most about 0.05). When the two modes differ, Ask mixes them by position in their own ranked list
(`KnowledgeMixer.rankScores`, 1/(60+rank) on both sides), never by raw score. The "complete once" memory of a corpus is dropped when
the choice leaves the search model, so coming back waits for the coverage again. A meeting whose embedding job failed for good (six attempts) and
that has no vectors counts as neither covered nor missing, so one such meeting cannot keep Ask on keywords for good; changing the settings
forgets the failed job and it counts (and is tried) again. A question the model cannot embed (all zeros) is
answered by keywords.

The 0.30 and 0.15 come from spike 9c on synthetic data (80 codes, 60 names on an English background) and are frozen. The
unweighted extras are not measured. Before release a held-out check on real, ASR-noisy transcripts must pass (R@3 against
Gemma alone: lower 95% bound of at least -0.02; bare-code hit@1 of at least 0.95; no regression on "what did X say"). If the
name part fails, `SemanticRanker.nameBoost` becomes 0 (one constant) and only the code part ships.

## The MLX dependency

Package.swift has exactly one package: `https://github.com/MaquinaTech/mlx-swift.git`, pinned by revision
`999f159e905affa3cc25bc1127a6cb489a5ffbb9` (branch `vauta-clt`). It is ml-explore/mlx-swift 0.32.3
(`19601207e9a0de51e03ee6ec0c3c5f3784275075`, vendoring mlx v0.32.2) plus two patches so that it builds with the Command Line
Tools only (the stock build needs Xcode's `metal`):

1. `Package.swift` of the fork excludes `mlx-generated/metal` (no Metal toolchain exists with the Command Line Tools) and builds the generated
   embedded kernel source (`runtime_default_kernels.cpp`) instead.
2. `Device()` never looks for a metallib when the embedded sources exist; `runtime_default_library_(name)` looks the kernel up
   in an exact table of 167 names (arg_reduce 24, conv 36, dot 3, layer_norm 12, random 2, rms_norm 12, rope 18,
   scaled_dot_product_attention 57, fence 3), compiles only that group, once, lazily, and throws for an unknown name.
   The 516 KB source is generated by flattening mlx's Metal files; its SHA-256 starts `5b9c64da` and ends `07151`.

`scripts/check-dependencies.sh` (CI, and a test) fails on any other pin. `THIRD_PARTY_LICENSES.txt` lists every licence file of
the compiled packages (`scripts/list-third-party-licences.sh`).

**Bump procedure** (never change the pin otherwise): fetch the new upstream release; re-apply both patches; regenerate the
kernel source and the name table (they need a Metal-capable Mac, once); build with the Command Line Tools; run
`Vauta mlx-selftest` (59/59) on an unsigned build and then on the locally signed bundle (`scripts/setup-signing.sh`), on an M1-class Mac and an M5
(the NAX kernels are untested), and after each macOS major release; run `Vauta mlx-selftest --model` with the model installed;
tag both fork commits (`MaquinaTech/mlx-swift` and the `MaquinaTech/mlx` commit its `Source/Cmlx/mlx` submodule names, now `d1dfda2`; for example `vauta-0.9.0`) so
neither can become unfetchable, and name both in NOTICE and SECURITY.md; update the revision in Package.swift, `Package.resolved`, `scripts/check-dependencies.sh` (also `MLX_CORE_REVISION`, the `MaquinaTech/mlx` commit, and `MLX_C_REVISION`, the `mlx-c` commit the fork's `Source/Cmlx/mlx-c` submodule names, now `ebc88f1`), NOTICE and
`THIRD_PARTY_LICENSES.txt`; run the whole test suite with `VAUTA_SEARCH_MODEL_DIR` pointing at an install.

**Hardened runtime**: runtime compilation of Metal source is expected to work under the hardened runtime and the sandbox
without any new entitlement (it runs in Apple's compiler service). If `Vauta mlx-selftest` fails in a signed build, do not add
JIT, unsigned-memory or library-validation entitlements (AGENTS.md rule 5): stop and report.

## The self-test

`Vauta mlx-selftest [--model]` is a hidden command (not in `--help`) that exists in release builds, because it must run in the
shipped binary. It opens no store, records nothing and uses no network. It prints the number of kernel checks that passed, the
device, the first-compile time and whether the process is sandboxed and hardened; with `--model` it also verifies the files
and embeds 8 fixed public sentences against stored fp32 vectors (cosine at least 0.999). Exit codes: 0 pass, 1 fail, 2 no
supported GPU, 3 model missing (with `--model`). `VAUTA_SELFTEST=1 scripts/build-app.sh` runs it on the built bundle
(`VAUTA_SELFTEST=model` adds `--model`). The app runs the 17-check encoder subset once per launch before the first load; a failure
means keyword search only.

## Tests

Tests never download the model. They use a synthetic three-block model, a tiny hand-built tokenizer and a fake encoder, plus a
`URLProtocol` stand-in for Hugging Face and its CDN. Tests that need the GPU skip without one; tests that need the real files
run when `VAUTA_SEARCH_MODEL_DIR` names an install folder (the one holding `model.safetensors`) and
`VAUTA_SEARCH_TOKENIZER`/`tokenizer.json` there: the tokenizer goldens, the fp16 encoder against the stored fp32 vectors,
the fp32 retry, the token-id bounds and the memory run.


## Launch behaviour, ranking details and known limits

- **Preparing at launch.** After `start()` finds an install, the controller loads it in the background (the full check of the
  files, the tokenizer, the encoder, the kernel self-test and warm-up, about 3 s) and the card says "Preparing" until it is
  ready, so the first question does not wait. It does nothing during a recording (or two minutes after), in Low Power Mode or
  when the Mac is hot (on battery it does load: loading once is not bulk embedding); Ask and the sidebar search ask again (Ask after 300 ms on screen, the sidebar when the person types). The
  model unloads after 3 idle minutes and loads again the same way.
- **Planning chunks needs only the tokenizer.** `chunkBudget()` and the token counts load and verify `tokenizer.json` (size and
  SHA-256, about 20 ms) and never build the encoder, so reconciling embeddings at launch or after a recording does no GPU work. The
  tokenizer is verified at every load and its size at every launch (`quickCheck`); the import verifies its staged copy.
- **Items the model cannot embed** (a window that is only whitespace, a row that stays NaN after the fp32 retry) are stored with a
  marker (an all-zero vector with scale 0, which no index loads) so they count as covered, are not retried on every pass and the
  index can complete. Settings says how many ("Items the model couldn't read"); keywords still find them.
- **The relevance floor** of related meetings, related documents and the sidebar's "By meaning" group is a cosine of 0.65
  (`SemanticRanker.relatedFloor`). Measured on the spike 9b vectors (256 dimensions, int8): unrelated texts have a mean cosine of
  about 0.53 and 0.64 at the 99th percentile; the best relevant passage of a query has 5th percentile 0.69 to 0.77 in monolingual
  sets (0.63 across languages). The floor removes the noise of random pairs and keeps about 95% of relevant first hits. It cannot
  tell "nothing relates" from a near-topic passage: the best passage of a large unrelated corpus reaches 0.67 to 0.72. The
  earlier 0.55 was below the mean of random pairs and filtered nothing.
- **Parity goldens.** The 256-d goldens in `SearchModelGoldens` come from Hugging Face's reference stack (sentence-transformers, fp32 on
  CPU, no Vauta code), made by `tools/search-model/make-goldens.py` with the pinned versions in `requirements-goldens.txt`; Vauta's
  fp32 encoder matched them at cosine 1.00000 on all eight sentences. `reference` is true, so `mlx-selftest --model` checks the
  app against an independent reference. The model-gated tests are skipped with a reason, not passed, when `VAUTA_SEARCH_MODEL_DIR` is not set.
- **Free space.** The preflight asks for the download plus 256 MiB (843 MB); a write that runs out of space reports what is still missing.
- **The live-answer gate (E2).** When the search model ranks a source, the evidence gate of a question heard in the meeting compares the passage's **raw cosine**
  (`RetrievedPassage.cosine`, `DocumentPassage.cosine`: no code, name, entity or note boost) with the threshold of that source (this meeting, past meetings,
  documents), all in `QuestionEvidenceGate.Thresholds`; two shared content words still pass a source without any cosine. The earlier single threshold of 0.45
  was compared with the boosted score and was below the mean cosine of two unrelated texts (about 0.53). A passage that has no vector yet (a meeting recorded minutes ago,
  paused while recording) is ranked by keywords with a placeholder score; it has **no** cosine (`nil`), so it can only pass on shared words. The thresholds are 0.70 for this meeting, past
  meetings and documents (`QuestionEvidenceGate.calibratedMeetingThreshold`, `provisionalDocumentThreshold`; documents are provisional, no evaluation set covers them).
  The value is where the cosine rejects unrelated meetings (13% / 4% of them pass at 0.70, development / held out, against 43% / 48% at 0.65) and heard questions in the
  meeting's language still pass (0.90 / 0.85). It is not a precision target: the cosine only rejects **unrelated** sources. A meeting on the same subject that does not hold the answer
  scores like one that does (AUC of the best passage 0.77 and 0.69; 0.70 and 0.43 for a question the series never answered, 17 and 11 questions), so no threshold catches an on-topic
  unanswerable question: that is the job of answer verification. The first value, 0.78, was calibrated on typed questions; it passes only 24% / 5% of heard answerable questions
  (cross-language 0.10 / 0.03) and its balanced precision fell from 0.91 (development) to 0.81 (held out), so it was dropped. The cross-language heard questions score about 0.045 lower
  than same-language ones and need the translated question for the shared-words path (implemented for keyword-ranked sources, E4 below).

  Pass rate of the gate (best passage's raw cosine, or two shared words) by threshold, development / held out (the "another session" column is the cosine only):

  | tau | heard, same language | heard, cross-language | the same question over another session (cosine only) | unrelated meeting | unanswerable (typed set) |
  |---|---|---|---|---|---|
  | 0.65 | 1.00 / 0.98 | 0.96 / 0.80 | 0.97 / 0.90 | 0.43 / 0.48 | 1.00 / 1.00 |
  | 0.70 | 0.90 / 0.85 | 0.49 / 0.27 | 0.71 / 0.64 | 0.13 / 0.04 | 0.76 / 0.91 |
  | 0.72 | 0.84 / 0.77 | 0.31 / 0.12 | 0.53 / 0.42 | 0.06 / 0.04 | 0.65 / 0.82 |
  | 0.78 | 0.67 / 0.58 (shared words alone: 0.65) | 0.10 / 0.03 | 0.09 / 0.10 | 0.00 / 0.00 | 0.00 / 0.27 |

  (Positives are heard questions; the negatives are typed questions, there are no heard-question negatives. Of the typed answerable questions the cosine path alone passes
  48% / 62% at 0.78; of the heard ones, 24% / 5%.) A passage that held the question
  itself (or what was said after it) is scored again from the lines that are left (`cosineWithoutQuestion`), so a question never finds itself; the leak raised the best-passage
  cosine by +0.024 / +0.025 (development / held out) with almost no effect on recall. That cosine is computed from the vector rounded the way the index stores it and at interactive priority
  (`SearchModelEngine.interactiveDocuments`); a model that cannot embed the lines, or answers in another space, gives no cosine and the passage does not pass on it. This only matters
  once the live meeting ranks by meaning (E3), because until then a meeting being recorded has no vectors and its source is judged by shared words alone.
  Without the search model nothing changed.

## Evaluating retrieval

`Vauta llm-eval --tasks retrieval` (hidden, EVALUATION ONLY, no language model, no network) runs the app's own retrieval over public question sets and writes, per
query and arm, where the gold segments are among the passages that fit Apple's Ask budget (3 passages, `ContextBudget(contextTokens: 4096)` characters) and at
ranks 1 to 10, plus the raw cosine and shared words of every passage so the gate's threshold can be swept offline. `--search-model <install folder>` (the folder
holding `model.safetensors` and `tokenizer.json`) loads the search model after checking the sizes and SHA-256 of both files against the pins above. A throwaway
`UserDefaults` suite keeps the "coverage reached" markers of every evaluation out of `UserDefaults.standard`.

```
Vauta llm-eval --tasks retrieval --sets <data folder> --out <folder> [--search-model <install folder>] \
    --retrieval-arms K,S,S3,T,Tref,S3T,S3Tref,S3MMR,S3leak --retrieval-sets w11,w11-stress,w10,cross [--split dev|test] [--max-queries n] [--sweep 0.45,0.5,…]
Vauta llm-eval --tasks retrieval-controls --sets <data folder> --out <folder> --search-model <install folder> [--controls miracl_es,miracl_en,miracl_ja,mlqa_es_to_en,mlqa_en_to_es]
```

Arms: **K** keywords (today without the model); **S** the model as shipped (earlier sessions embedded, the meeting being recorded not, because a meeting is embedded
once it ends: for questions about the meeting being recorded it equals K); **S3** the visible prefix of the meeting embedded too (what embedding during the
recording, E3, would give); **T / Tref** keywords with the query translated into the meeting's language by Apple's on-device Translation (`T`, installed languages
only) or by the reference translation of the set (`Tref`, an upper bound); **S3T / S3Tref** the same with S3; **S3MMR** S3 with the passages chosen by maximal marginal
relevance (E5); **S3leak** S3 without the self-match fix, to measure it; **S3od** the app's own on-demand code (E3 on demand, below), not a simulation, typed questions only. `--tasks live-questions --search-model` also embeds the earlier meetings of a series.

`run.json` records the thresholds the live rows were gated with (`liveThresholds`, and `live_tau` in each live row), because `passing` and the live budget recall depend on them; `--live-tau 0.70`
sets one value for every source instead of the binary's own.

### Results (E1 to E5, 2026-10-18, independent judge)

Retrieval only, on public sets (AMI-derived heard questions, typed questions, a cross-language set whose translations were constructed and not reviewed by a person, a 3-session
stress set), Apple's Ask budget of 3 passages and 4,596 characters (context size assumed 4096; the real system value on this Mac was not read). Intervals are percentile bootstraps by meeting,
paired by question. There are few clusters (heard-question test set 9 meetings, typed-question test set 5, the stress set 1) and no correction for the many cells, so only the large, consistent effects should be trusted.

- **E1, typed Ask during recording on Apple's model, S3 minus S** (the prefix of the meeting embedded, E3, against today's keyword ranking of the meeting being recorded): +0.076 [+0.001, +0.161]
  same language (n 120; borderline), +0.300 [+0.157, +0.459] on long meetings (3 sessions, n 34), +0.432 [+0.362, +0.507] cross-language. With the integrated model or a server the prefix
  fits whole (157/158 at about 20K tokens), so E3 changes nothing there.
- **Live heard questions:** at a threshold of 0.75 or more, same language: +0.020 to +0.040, intervals include 0 (no measurable gain). Cross-language: +0.006 [+0.000, +0.017] at 0.80 and +0.057 [+0.029, +0.093] at 0.75, small but above 0, and translate-first is better there. At 0.70 the gain is +0.114 [+0.028, +0.194] same language
  and +0.124 [+0.058, +0.189] cross-language, but it comes from opening the gate, whose net value is not measurable without heard-question negatives. Live answers run on the integrated model or a
  server, where the whole meeting usually fits: what E3 changes for them is the evidence gate, not the context.
- **E5, MMR:** no effect (S3MMR minus S3 within +-0.02 everywhere, intervals include 0). Not shipped.
- **E4, cross-language:** with the corpus embedded, search with the **original** query (S3 minus T, translate first: +0.098 [+0.028, +0.174] pooled, but +0.031 [-0.050, +0.123] on the held-out half); never feed
  a translated query to the semantic ranker (S3T minus S3: -0.019 [-0.056, +0.017]). When the corpus ranks by keywords (no search model, or the meeting being recorded today) translate first (T minus K: +0.334 [+0.224, +0.433]
  typed, +0.149 [+0.067, +0.230] heard; Apple Translation is about 0.06 below the reference translation; no translation failure with installed language pairs). **Implemented as the combined routing below:** the shared-words path of the live gate also takes the translated question when the source ranks by keywords
  (the gate passes 55% of cross-language heard questions with the translation against 3% without). For heard cross-language questions on the live path, at the shipped 0.70 translate-first is at least as good as embedding the meeting (S3 minus T: -0.026 [-0.161, +0.089]; at 0.75 it is -0.092 [-0.187, -0.012]),
  so at any threshold of 0.70 or more T >= S3 there; the recommended routing is by ranking mode (translate when the source ranks by keywords).
- **Controls** (rerank pools, not comparable with BENCHMARKS.md): MIRACL nDCG@10 0.648 (en), 0.675 (es), 0.728 (ja); MLQA cross-lingual 0.819 (en to es), 0.780 (es to en). The BM25 control is implausibly low
  (0.139 on English MIRACL, below Japanese): the pools look BM25-mined, so it must not be cited, and the cosine-minus-BM25 gaps say nothing about the app's keyword baseline.
- **E3 recommendation (conditional; on demand was chosen on 2026-10-18, see below):** go, narrowly. The measured benefit is typed Ask on Apple's model; an option is to embed the prefix on demand when such a question needs retrieval (about 1.6 to 3.3 s per meeting-hour, cached)
  instead of during every recording. Energy, latency and transcription drops were measured afterwards and passed in a simulation; the footprint inside the running app was not, so it is off by default (see below).
- **Not measured:** bulk embedding waiting behind a generation; E3 as it would run (whole chunks as they complete; the harness embeds the exact prefix, which overstates the gain on the last lines);
  heard-question negatives; Spanish heard questions (1 row); past-meeting (8 rows) and document (0 rows) sources; a human audit of the gold and the 241 constructed translations; end-to-end answer quality and the false-card rate of any threshold;
  the latency of Apple Translation on the live path; the real Apple context size on macOS 27.

## E4 in the app: combined routing

`QueryRouting.route(mode:question:corpus:)` decides which text a ranker searches with, per corpus (`LLMService+QueryRouting.swift`):

| Corpus ranks by | Query | Why |
|---|---|---|
| meaning (`.semantic`) | the question as asked | a translated query to the semantic ranker hurts slightly (S3T minus S3 -0.019 [-0.056, +0.017]) |
| keywords (`.keyword`: no search model, still indexing, or the meeting being recorded when a question is heard in it) | the question translated into the transcripts' language | T minus K +0.334 typed, +0.149 heard |
| a server's fusion (`.rrf`) | the question as asked | one query feeds both halves of the fusion; not measured |

The translation (`QueryTranslator`) uses Apple's Translation through `TranslationBackend`, installed pairs only (it never downloads a language and
never contacts a server), waits 2 s for Ask and 1.5 s for the live gate, remembers the last 64 translations and the translator of each pair, and leaves
a pair that failed alone for 30 s. A translation that is late keeps the translator (the first call of a session can be slow while Apple loads its model); only two late ones in a row leave the pair alone for 30 s. Any failure, a pair that is not installed, an empty result or a question whose language is not known with
confidence (`OutputLanguage.confident`) means the question is searched as asked. The target is the language of the meeting being asked about, or, over
the whole library, the one language all meetings share (with two languages in the library there is none, and the question is searched as asked). The
model that answers always gets the original question: only retrieval sees the translation. The live gate counts shared words in the translated question for
a keyword-ranked source; for a source ranked by meaning it keeps the original (the effect of translating the shared-words check there is not measured).
Documents are searched as asked (their language is not known per file).

## E3 on demand: the meeting being recorded

Since 2026-10-18 the meeting being recorded is not embedded during the recording. When a person types an Ask during a recording and the
answering model cannot hold the lines said so far (Apple's 4K window; with the integrated model or a server the prefix fits whole and changes
nothing), `LLMService.embedLivePrefix` embeds the **closed chunks** of the visible meeting (all but the last, which is still growing and is found by
keywords) at interactive priority, in the question's turn:

- cached and incremental: closed chunks are stored in the meeting's own chunks, keyed by start and a fingerprint of their text, so the next question embeds
  only the chunks that closed since (a chunk whose text changed, a speaker named, is embedded again and the stale one dropped);
- nothing runs unless a question is typed (not for heard questions, documents-only questions or other meetings), the search model is the embedding provider and
  is ready, the Mac is not on battery, in Low Power Mode or hot (`IndexerPolicy.allowsOnDemandEmbedding`: the same rules as bulk embedding, except that the recording
  itself does not stop it, because the person asked and the work is bounded and cached), and, over the whole library, the library ranks by meaning;
- the Mac's state is asked again before every batch (about 13 batches for a cold 120-minute prefix), not only once: a Mac that goes on battery, enters Low Power Mode or gets hot in the middle stops there, and the batches already stored stay (`aMacThatGoesOnBatteryBetweenBatchesStopsTheEmbeddingAndKeepsTheBatchesAlreadyStored`);
- a typed question whose embedding is skipped (battery, Low Power Mode, heat, the model being deleted) searches the meeting by keywords with the translated question, even if an earlier question stored chunks: they are stale and the lines said since have none. For a question about one meeting that is the meeting being recorded, the ranking is switched to keywords; for a question over the whole library, the chunks that an earlier question stored for the live meeting are removed (`LLMService.discardLivePrefixChunks`), so the semantic pass cannot rank it by them and its lines come from the keyword buckets alone (`aWholeLibraryQuestionThatIsSkippedDoesNotRankTheLiveMeetingByTheStaleVectorsOfAnEarlierOne`). A switch that is off stores nothing, so nothing is removed;
- after a crash during a recording, the chunks left by typed questions (the memory of which meetings hold them died with the app) are removed at launch for the interrupted meeting, so a partial set is not counted as covered; the embedding job, or the reconcile when the search model is not ready yet, writes the whole set (`chunksLeftByAnInterruptedRecordingAreDiscardedSoThePartialSetIsNotCovered`);
- the chunks belong to the recording: the meeting is marked as holding them before they are stored, and when the recording ends (also while they are being stored) only that meeting's chunks are removed;
- it stops with the question (cancellation) and with the recording (a batch in flight is not stored); any other trouble, a store error included, is a skip and the answer goes on with keywords;
- **a question heard in the meeting is not affected.** The meeting being recorded keeps ranking by keywords on the live path (with the translated question for the shared-words check, E4),
  whatever chunks the typed questions stored: they stop at the last typed question, the lines after it would only be reachable through untranslated keyword buckets, and the measured live path
  (S3 minus T -0.026 [-0.153, +0.087] cross-language; E1 found no gain for heard questions) is keywords with translation. Test: `aQuestionHeardAfterATypedOneStillUsesTheTranslatedKeywordSearch`;
- **when the recording ends the on-demand chunks are removed.** They stop at the last typed question, so a meeting that holds them is not "covered": until the embedding job after the meeting writes
  all its chunks (it waits two minutes after a recording, and while on battery or in Low Power Mode) the meeting ranks by keywords like any meeting that has not been embedded yet,
  does not count towards the index coverage and cannot set the "coverage reached" marker early. Test: `whenTheRecordingEndsTheMeetingIsNotCoveredUntilTheEmbeddingJobWritesItAll`;
- hidden preference `searchModelEmbedLivePrefixOnDemand` (`LLMService.embedLivePrefixDefault`, **false**: off; `defaults write <bundle id> searchModelEmbedLivePrefixOnDemand -bool YES` turns it on).

**Status: off by default (2026-10-18).** The rule was to measure energy, RAM and latency before enabling it, and to keep it off if the added RAM pushed past the memory gate or transcription dropped chunks. The measurements below
passed, but they were made with the embedding in a separate process and the app was not run, so the following were never measured: the memory footprint of the app during a real recording (microphone and system audio, diarization and live
notes on) with a typed question at 60 and 120 minutes (headroom to the engine's 1.4 GB governor is about 350 MB on top of what a recording already holds), the app's own dropped-chunk counter on a real recording, and a battery-powered Mac
(on battery the question now skips the embedding, so only a Mac on the charger is affected). It goes on by default after one real in-app recording has been measured, or when the maintainer decides to enable it with those caveats.

## Item vectors (links to earlier meetings)

With links on, the second `embed` job of a meeting embeds its eligible tasks and decisions (their own words only, `.document` purpose, int8, table `item_vectors`, one space per model) and up to 300 earlier ones. A pair needs a raw cosine of at least the floor (0.90, set on the development split) and one shared content word; items in different languages are never paired. Deleting the search model deletes these vectors (the links stay). Vectors from a model server are never used for links.
