# The integrated language model

Vauta has one optional language model that runs inside the app: **Gemma 4 E4B-it** by Google on MLX Swift. It is
never bundled and never downloaded without the person asking. It was built in steps: first behind a hidden flag (the first build,
measured 2026-10-12 and 13), then fixed after a blind A/B (2026-10-13), then given its interface (Settings → Models, opt-in on Macs
with 16 GB or more, never the default and never called "recommended") and the work that makes it fast and faithful while a meeting is
recorded (2026-10-14, see "The interface, reading while recording, recall and guards"). This page is the reference for what is pinned,
how the file is built on the Mac, how the model runs and how it was measured, in the order the work was done.

User-facing summary: PRIVACY.md and README.md. Search model: [SEARCH_MODEL.md](SEARCH_MODEL.md), whose pinning,
download and import code this follows.

### How the manifest was derived (2026-10-12, Mac mini M2)

`make-manifest.py` streamed the whole 16 GB file once with HTTP Range (4 parallel connections, about 27 MB/s, 593 s), never storing
it, and in that pass:

- hashed the whole file: it equals the LFS oid `cfbd3d2f…`;
- hashed the header, every 64 MiB block of the tower and every source tensor;
- quantised each matrix with the numpy port of Vauta's algorithm (`affine_quant.py`), writing the output at its final offsets;
- quantised every 16 MiB row chunk again with `mx.quantize` on the GPU and on the CPU (mlx 0.32.3) and counted differences:
  **GPU: 0 differing words, scales or biases of 932,806,656 words and 116,600,832 groups**; CPU: 12,139,525 words (1.3%) and 80,005
  scales differ, which is why the algorithm mirrors the Metal kernel and not MLX's CPU one (see below);
- compared its 1,355 output tensors with the spike's mlx-community conversion (`mlx_vlm`, a different revision of the same
  weights): **1,355 of 1,355 byte-identical**.

The reference conversion in the brief turned out to be `mlx-community/gemma-4-e4b-it-4bit` made with `mlx_vlm.convert` from revision
`fee6332c…`, not `mlx_lm convert` from `ee0ef602`. The weights file and the tokenizer have the same LFS oid at both revisions, so it is
a valid per-tensor reference for the weights; the chat template differs (18,569 bytes at the pin, 17,336 there) and Vauta checks
against the pinned one.

## Download, quantisation and import

`LanguageModelDownloader` follows `SearchModelDownloader` step by step (purpose `modelDownload`; a 302 that is validated and never
followed; the CDN host allowlist; `Accept-Encoding: identity`; exactly `206` with the exact `Content-Range` and length; a signed URL
that lives in memory and is resolved again once on 403 or 410). Differences:

1. The tower is **not stored**. Each 64 MiB Range block is held in memory, hashed as it arrives and compared with its pinned hash
   before any byte reaches the quantiser. A block that does not match is fetched once more after resolving again; a second mismatch
   deletes everything.
2. `StreamingQuantizer` consumes the verified bytes in order, in row chunks of at most 16 MiB, while the next block downloads. It
   writes each output tensor at its pinned offset of a file preallocated with the pinned header (so the sorted output order does not
   matter), and checks each output tensor against its pinned hash as soon as it is complete. At the end the whole file is checked
   against the pinned SHA-256 (about 5 s for 4.2 GB). Only then is `model.safetensors.partial` renamed.
3. `progress.json` stores the span offset of the first chunk not written. A resumed download restarts at the block that holds it,
   verifies the whole block and skips the bytes already consumed. A test resumes at six cuts and always ends with the same bytes.
   On resume the output tensors completed before that point are read back and compared with their pinned hashes (about 4 s for
   4.2 GB): a torn write or a flipped bit moves the restart back to the first damaged tensor, so only its source bytes are fetched
   again. A tensor that was in progress is checked when it completes (a failure there still starts over).
   A cancelled or failed run stops the background quantiser and waits for it before it returns, so Resume never has two writers on
   the partial file.
4. Free space needed: the assembled file, the tokenizer and 512 MiB (4.77 GB, shown as "about 4.8 GB") less what staging already holds; a write that runs
   out of space reports what is still missing. Only the language model's own folder counts (not the search model beside it), and
   what counts is the space allocated on disk, because the `.partial` file is created at its full 4.2 GB and fills as the download
   goes (its logical size says nothing about what is written).
5. The hardware gate: 16 GiB of memory or more and an Apple7 GPU or later; below that, download and import are refused with a reason.

The three provenance headers of the 302 (`X-Repo-Commit`, `X-Linked-Etag`, `X-Linked-Size`) must equal the pins **when Hugging Face
sends them**, as for the search model (docs/SEARCH_MODEL.md); a response without them is accepted. This is a deliberate deviation
from "must be present": the commit is already in the pinned URL, and integrity never depends on the headers, because every 64 MiB
block and the assembled file are hashed against pins.

**Import** (`LanguageModelImporter`, symbolic links followed as in the Hugging Face cache) takes Google's original
`model.safetensors` (header hash, every block, the whole-file SHA-256, then the same quantiser, no network), a 4-bit file assembled on
another Mac (checked against the pinned size and hash) and `tokenizer.json`.

**Store**: `<Application Support>/Vauta Models/gemma-4-e4b-it/ee0ef602/` with `model.safetensors`, `tokenizer.json` and
`installed.json`; directories 0700, files 0600, excluded from backups and Spotlight; Erase Everything keeps it; delete unloads first.

### The quantiser is deterministic CPU code that matches the GPU

mlx-lm quantises on the GPU, and Metal's `affine_quantize` differs from MLX's own CPU kernel in two ways that change the bytes: the
group minimum starts at the bf16 maximum and the group **maximum starts at 0**, and rounding is half **away** from zero (`round`),
not half to even. `AffineQuantizer` mirrors the Metal kernel in IEEE fp32 with no fused operations:

    lo = min(bf16max, min(group)); hi = max(0, max(group))
    scale = max((hi - lo) / 15, 1e-7); side = |lo| > |hi|; scale = side ? scale : -scale
    edge = side ? lo : hi; q0 = round_away(edge / scale); if q0 != 0 { scale = edge / q0; bias = edge } else { bias = 0 }
    q_i = min(round_away((w_i - bias) / scale), 15); eight nibbles pack little-endian into a UInt32; scale and bias are stored as bf16

The result does not depend on the number of threads or on how rows are chunked, and it is byte-identical to `mx.quantize` on the
GPU for the whole model (above) and for 69 edge rows (`quantizer_goldens.json`: all negative, all positive, zero, constant, rounding
ties, extremes near the bf16 maximum, subnormals). A NaN or infinity in a source tensor is a hard failure.

## Running it

`Sources/VautaMLX/LLM` (the only place MLX is used) is a port of mlx-lm 0.32.0's `gemma4_text.py` for the pinned 4-bit file (MIT
notice in each file, NOTICE, THIRD_PARTY_LICENSES.txt): 42 layers, 8 query heads and 2 key/value heads, head dimension 256 for the
sliding layers (window 512, RoPE 10,000) and 512 for the seven full-attention layers (proportional RoPE, 64 rotated pairs,
`freqs = 10^6^(2i/512)` then infinity), GeGLU, per-layer inputs, layers 24 to 41 reading the keys and values of layers 22 and 23, a
tied 4-bit output head with `tanh(x/30)*30`, bf16 activations and bf16 key/value caches.

- **Weights**: 2,492 MB resident. The 1.6 GB per-layer embedding table is never loaded: the rows of the tokens in a prompt are read
  from the memory map and dequantised on the GPU (about 6.2 KB per token).
- **Sliding caches** keep the last 511 tokens before a chunk; attention runs over those and the chunk with a windowed mask. This is
  the same set of keys as mlx-lm's rotating cache. **Full caches** grow in steps of 1,024 tokens.
- **Prefill** is chunked twice over. Memory: the largest power of two up to 512 whose unfused attention scores (heads x chunk x
  context x 4 bytes) stay under 256 MiB, because the fused attention kernel is not used at head dimensions 256 and 512. Time: the chunk
  is also cut to what the measured prefill speed does in 0.4 s (a multiple of 16, at least 16; the first chunk is 64 tokens, before a
  speed is known). At the measured 193 to 224 tokens/s that is 64 to 80 tokens, so cancellation, the gate and the heat check are
  looked at every 0.3 to 0.4 s, not after a 512-token chunk (2.3 to 2.7 s). Measured on the real model (release, 4,000 tokens,
  interleaved, load1 4 to 6): 512-token chunks 219 tokens/s, 256 218, 128 215, time-sized 205, so the guarantee costs 6 to 7% of
  prefill speed. Cancelling a 12,000-token prefill 30 s in was seen after 0.25 s (the GPU was shared at the time).
- **Kept prefix** (live answers and Ask): the state after `prefix - 16` tokens is kept (the last 16 are re-run so a token that merges
  across the boundary is right); the next request with the same ids up to there continues from it, the question and the answer are
  never kept. The tiny-model test shows identical text with and without it. There are two slots, **Ask** (interactive priority) and
  **live notes** (live priority), each with its own caches. Minutes, note expansions and every call that keeps no prefix run on scratch
  caches and leave both slots alone, so a recording that runs notes and live notes all the time no longer throws away the Ask prefix
  (a test runs Ask, live, minutes, live, Ask and checks that both prefixes are reused). Two calls on the same slot take turns.
  **A prefix that changed inside is rewound, not rebuilt.** A transcript changes under a live prefix (a partial segment finalised with
  other text, a speaker relabelled, entities added), so the engine uses the longest common prefix: it keeps checkpoints of the sliding
  windows (a copy, about 20 MB each on the real model) dense near the end of the prefix (every 512 tokens in the last 1,024) and
  sparse before it (every 8,192), cuts the full-attention layers back to the latest checkpoint at or before the first differing
  token, restores the windows, and prefills from there. That is exact, not an approximation, and costs the tokens between the
  checkpoint and the end of the prefix. An edit before the first checkpoint starts again. Tiny-model tests edit the prompt near the
  end, in the middle and early and check the same text as a cold run and `reusedTokens > 0`.
  **Memory**: the kept caches and checkpoints are counted (`cacheBytes`). A call that keeps no prefix (minutes) first frees kept
  prefixes until at most 512 MiB remain (the live one first); a call with a prefix of its own leaves the other one only while both
  fit in 1.5 GiB. Turning keep-warm off (the recording stopped) drops the live prefix, and the Ask prefix is dropped after the idle
  period even while a recording keeps the model loaded. Growing a full-attention cache still copies it once per 1,024 tokens (a
  transient 2x of 16 KiB per token: 1 GB at 64k, bounded and short); an in-place preallocation was not done.
- **Sampling**: greedy, or top-k 64, top-p 0.95 at temperature 1.0 applied after the grammar mask, with a seed derived from the
  prompt (SplitMix64, the same text on every Mac). The order is Hugging Face transformers' (temperature, top-k, then top-p over the k
  survivors), which is what the model card's generation config describes; mlx-lm applies top-p to the untempered distribution first, so
  at a temperature other than 1 its support can differ (a test pins the supports down on fixed logits). The loop guard stops a 32-token
  n-gram that repeats three times; in a constrained output it closes the value first (below).
- **Tokenizer**: `GemmaTokenizer` of the search model, unchanged for parsing and BPE, plus `encodeLiteral` (no special token is ever
  matched in content: a transcript line `<turn|>` is text), `decode` and `StreamingDecoder`. The chat template is built from ids
  (`GemmaChatTemplate`): `<bos>`, then for each message `<|turn>role\n` + trimmed content + `<turn|>\n`, then `<|turn>model\n`; thinking is
  off. 2,000 tokenizer goldens and 40 template goldens (rendered with the pinned Jinja template and HF `tokenizers`) are checked in
  `llm-selftest`.
- **One GPU job at a time** across this model and the search model (`MLXWorkGate`): interactive answer, live notes, minutes, bulk
  embedding in that order. A generation does not hold the gate for its whole length (minutes took 77 to 115 s): it takes it per
  prefill chunk and per burst of 16 decoded tokens (`GenerationLease`) and, at every checkpoint, gives it to a waiter of higher
  priority. A search query's embedding, or a live answer during a minutes job, therefore waits at most one chunk or burst (a test runs
  a 900-token generation and an interactive request: the request is served after about 60 tokens, and a live generation finishes inside
  a minutes one). Everything that touches the GPU in `LanguageModelEngine` goes through the gate, the kernel self-test and the weight
  load included (a source test checks every entry point). The engine itself is an actor that stays free between checkpoints.
- **Heat** (`ThermalPolicy`): at `serious` minutes and bulk work give the gate up and wait, cancellably, until the Mac is below
  `serious`; live notes slow down (a 250 ms pause per step) and at `critical` wait; an interactive answer is only slowed down at
  `critical`; an answer to a question heard (optional work) does not wait: at `serious` it gives the gate up and ends (`GenerationTooWarm`,
  closed as stopped), so it never holds the model while the live notes wait behind it (a test with an injected thermal state checks that
  the gate is free and a live job runs). The state comes from `ProcessInfo.thermalState` (injected in tests).
- **Residency**: kept loaded while recording (the recorder calls `LanguageModelAccess.setRecording`, which keeps an engine that
  is loaded from unloading for being idle and loads nothing), unloaded after 5 idle minutes (never during a generation), on critical memory pressure
  and on delete. The pressure source has its own queue; the unload runs at the next checkpoint and the running generation stops there
  instead of holding the weights. The MLX cache limit is raised from 128 to 256 MB and the memory limit to 75% of the GPU working
  set only while the model is loaded; both are put back on unload. Those allocator changes, the cache clear and the search model's
  load (weights and kernel self-test) all happen under the same gate as every other piece of MLX work, so two queues never encode
  on MLX's one stream at once. The app has one engine (`LanguageModelAccess.engine(for:)`), shared by chat and the controller, so
  Delete unloads what chat uses.
- **Damaged files**: the quick check at launch (sizes, header) cannot see a flipped byte in the body. If the full check on the first
  load fails, the engine remembers it (no 4.2 GB is hashed again on every call), tells `LanguageModelAccess`, which stops offering the
  model (`.unavailable("damaged")`), so chat goes back to Apple's model at once. `LanguageModelController` is the state machine for
  Settings (2026-10-14): not installed, unsupported, downloading, paused for a recording (and two minutes after, like the search model),
  partial, verifying, ready, damaged, failed, deleting. It starts nothing by itself; the download is the person's click.

### Constrained decoding

`OutputSchemas` holds the formal schemas of every JSON output (`minutes`, `minutesExtract`, `liveNotes`, `noteSingle`, `noteBatch`,
`answer`, with `documents` variants), with the keys in the order the prompts show, and builds the per-call restrictions from what the
call site offered: `seg` is one of the segment numbers sent, `owner_id` is one of the people offered or `null`, an entity's `id` is one of
the people and projects offered (never `null`, from 2026-10-13), `due` is a
`YYYY-MM-DD` date or `null`, document citations are the `"S123"` / `"D2"` strings sent (the Ask prompt shows `"citations": []` and says in words that they are S or D and a number: no sample id to copy). `SchemaGrammar` compiles a schema to a
byte-level pushdown automaton; `TokenMaskEngine` turns the state into a mask over the 262,144 tokens (string interiors from a table keyed by
the string's small state, shared between calls; everything else by walking a vocabulary trie, which prunes at once). Keys, colons,
commas and braces have one possible continuation, so they are written without asking the model (`forcedSequence`: several tokens in
one forward pass); the first token must be `{` (no code fence), and after the closing brace the stop token is forced.

**Valid by construction, also when the output is cut.** (1) Strings never contain a UTF-16 surrogate escape (`\\uD800` to
`\\uDFFF`): written alone they are rejected by `JSONDecoder` and `JSONSerialization`, so the grammar refuses them at the second hex digit
and a character outside the basic plane is written as raw UTF-8. (2) When the token limit gets close, or the loop guard fires, the
generator does not stop in the middle of the value: it asks the constraint for the shortest valid ending (`GrammarState.shortestCompletion`:
close the string, `null` or the least value for each field still to come, the items an array still needs, the brackets) and writes it.
Near the limit that starts when the ending plus 64 tokens of slack reaches the room left (one token can lengthen the shortest ending by
less than that: a test measures it); in the middle of a character or an escape it lets the model write the few bytes that finish it. The
result keeps the finish reason `length` or `loop`, so the call sites' existing retry with a larger budget still happens, but the text is
valid JSON. (3) A state nothing can follow (a closed set with no member) ends the value at once; the schemas fall back to "any integer"
when an offered set is empty.

**Whitespace (2026-10-13).** The grammar compiles with bounded optional whitespace between tokens (`GFrame.ws`: at most 12 spaces or line
feeds in a row, after `{`, `[`, `,`, `:` and values; none after the closing brace, where the stop token is forced). Without it the
only bytes allowed after `"open_questions":[` were `]`, `]}` and a quote, but Gemma, trained on pretty-printed JSON, wants a line break
there: the nearest thing the mask allowed was the quote of a string, and the model then wrote its `]`, `}`, line breaks and fences
*inside* that string (the A/B found junk in the open questions of 32 of 39 minutes). The cost of whitespace is that keys are no longer
forced in one forward pass (a few dozen extra decode steps per call); the mask cost is unchanged (p50 0.02 ms). Pilot, decided in favour
of whitespace (below): the compact grammar with the pretty prompt, the compact grammar with a compact prompt, and whitespace with the
pretty prompt. `Vauta llm-eval` and the app build their constraints with whitespace; `SchemaGrammar(_, whitespace: false)` is the old compact
grammar (tests, and the way to see the defect: `LanguageModelRealJSONTests`, on the real 262k vocabulary, shows which layouts each
grammar can write and which tokens each offers after `"open_questions":[`).

**A field that decides the rest (2026-10-13).** `OutputSchema.tagged` is an object whose first key holds one of a few JSON words and whose
other properties depend on the word; the grammar walks a trie of the words and, at the end of one, continues with that word's
properties. The answer uses it (below). `shortestCompletion` picks the cheapest valid ending over all words (a cut-off answer closes
as `found:false` with no claims only if that is cheaper than one empty claim).

Deviations from the design, on purpose: string limits are in UTF-8 bytes (twice the character cap of the validators); the optional
quote-in-segment automaton is not implemented, and 2026-10-13 found a reason not to build it: with the quote forced to be a substring of the
cited segment the check "the quote is word for word in the segment" could no longer catch a made-up decision (the model would quote
whatever is in the segment it picked), so building it would loosen the verification it was meant to help.

The app's call sites set `ChatOptions.outputSchema`; only the integrated model reads it, so Apple's path and the server path are
unchanged. The repair retries stay as a safety net.

### Due-date rule (all providers)

A task whose `due` is the meeting's day or the day after, with nothing in the cited segment that says so (`MinutesVerifier.dueIsInSegment`),
loses its due date and keeps the task (before: the date stayed, marked unconfirmed). It targets the model that copies the meeting date.

## Parity with mlx-lm

`llm-selftest --model` without `--goldens` verifies the files and loads the tokenizer but runs no parity check: it prints
`parity: SKIPPED` and exits 5, which is not a pass. A release check must run it with `--goldens tests-fixtures` (the folder
`Tests/VautaCoreTests/Fixtures/LanguageModel`). With `--long` it also compares the last-position logits of a 31,617-token prefill
(`logit_goldens_long.jsonl`, made by `tools/language-model/make-goldens.py <folder> <template> <sets> - <long.jsonl>` from mlx-lm on
the same assembled file) with the same limit, so the many-chunk growth of the full-attention caches and the windowed masks past the
8.5k tokens of the other goldens are checked too.

The goldens were made with 512-token prefill chunks. The app now sizes chunks by time (64 to 80 tokens), so `llm-selftest` checks twice:
with 512-token chunks (`setPrefillChunk`) tokens and logits against the goldens, as above; and with the app's chunks it requires top-1 on
8 of 8 and the top-20 within the same limit and *reports* the greedy agreement (a near tie can flip with bf16 rounding when the chunking
changes, as it does in mlx-lm itself). The tiny-model CI test compares one pass over the whole prompt with the 20 best logits (within 3% of
the largest logit, same five best tokens, same twenty) and 16 greedy ids of 24 stored.

On the real file, 8 prompts (English, Spanish, German, Japanese, a multi-turn chat, 2,015 and 8,534 tokens of public AMI text, a
JSON-minutes prompt): the top-1 token matches on 8 of 8, the first 32 greedy ids are identical on 8 of 8, and the largest difference
over the top-20 logits is 0.06 to 1.06 (logits near 25 move in bf16 steps of 0.125). The brief's 0.05 tolerance cannot be met by any
bf16 implementation: **mlx-lm differs from itself by up to 1.09 on the same 404-token prompt when its prefill chunk changes from 512
to 128 tokens** (and 0.25 on 2,015 tokens). The self-test's limit is therefore 1.25 with identical top-1 and greedy ids.

That limit is wide on purpose, so a systematic error smaller than it could pass the real-model check. The tiny-model CI test is the
tight one: it agrees with mlx-lm to 0.0, 0.125 and 0.1875 on logits near 28 (5, 40 and 120 tokens, every layer type, the window wrap,
shared keys and values, proportional RoPE, per-layer inputs), and its bound is 2% of the largest logit, about three bf16 steps. A
float32 reference of the real model (mlx-lm and the port both in float32) was not built: the port's constants are bf16 by design, so
it would need a dtype-generic port and a second reference run.

## The blind A/B (2026-10-13): what it found and what changed

The blind judgement of the first build's A/B found the integrated model clearly better on live answers (0.83 against 0.40) and
its minutes not shippable (junk in the open questions of 32 of 39 runs, topics starting with "- ", 53 of 80 items dropped for reasons
nobody could see), and the two backends each had a defect of their own. These were fixed before the interface work. Everything below was
re-measured on the real models; the numbers are from a Mac mini M2 that was not idle, so times are biased upwards and
counts are not. The evaluation outputs are not in the repository.

### A. The junk in the minutes: a grammar without whitespace

**Root cause.** The grammar allowed no whitespace at all, and Gemma writes JSON with line breaks and indentation (the prompt shows it that
way in the first build; the shipped prompt is no longer pretty-printed, see the end of this section). After `"open_questions":[` the only bytes allowed were `]`, `]}` and the quote of a string. What the model wants there is a line
break, which was masked out, and the nearest thing the mask offered was the quote: it opened a string and wrote its `]`, `}`, line breaks
(as `\n`) and code fences inside it, sometimes a whole second copy of the JSON. That is why the first open question began with `]` or `}`
in 28 of 37 runs and why topics came with `-\n-\n- …` (a bullet list written into a string). `LanguageModelRealJSONTests` shows the
mechanism on the real 262,144-token vocabulary: after that `[` the compact grammar offers no token that is a line break, a space,
`]\n}` or `]\n`, and does offer tokens that start a string with `]` or `}` in it; the whitespace grammar offers `]\n}`, `]`, `\n` and a
space. It also shows that every layout of the minutes (compact, as in the prompt, closing brace on its own line, indented, with items)
and of the answer, with `"open_questions": []` and `]\n}`, is writable with whitespace, and that all but the compact one are refused
without it.

**Pilot** (4 meetings, one run each, Gemma, card sampling; ES2011d, IB4002 and TS3004b are `dev` meetings, cdm181025_a is a Spanish
council window): the compact grammar with the pretty-printed prompt (the first-build state), the compact grammar with the prompt showing compact
JSON, and the whitespace grammar with the pretty prompt.

| Variant | Decisions and tasks proposed / kept | Open questions (junk) | Topics (starting with "-") |
|---|---|---|---|
| compact grammar, pretty prompt (first build) | 11 / 1 | 22 (13) | 12 (5) |
| compact grammar, compact prompt | 5 / 1 | 6 (4) | 14 (8) |
| **whitespace grammar, pretty prompt** | **14 / 10** | **9 (0)** | **20 (0)** |

Showing the model compact JSON did not help (it was slightly worse): the prompt is not the cause, the mask is. **Decision: bounded
whitespace in the grammar** (at most 12 spaces or line feeds in a row, `GFrame.ws`), and it costs nothing measurable
(masks per call 380 to 687 against 300 to 1,018, p50 0.02 ms, wall times unchanged). Keys are no longer forced in one forward pass; the
extra decode steps are a few dozen per call.

**What the prompt looks like now.** The pilot's winning prompt was the pretty one, but the prompt that ships is not: while removing the
placeholders that Apple's model echoed (section C), `minutesJSON`, `extractJSON` and `digestJSON` became one line with empty values
(`"title": "", ... "topics": [], ... "open_questions": []`; zeros for numbers), so there is nothing to copy and no layout to imitate.
The pilot never measured exactly this combination (whitespace grammar with the compact, empty-valued prompt). It is measured by the
runs made after all the fixes: B (six meetings, Gemma) and D (16 meetings, Apple); their numbers are the ones to read for the shipped
state, and the table above only shows why the mask, not the prompt, was the cause. (The shapes show `[]` and not `[""]`: a model that
copied the latter wrote empty items. An empty string is skipped by `MinutesText.list` without being counted as junk, so `topic.junk` and
`open_question.junk` count real junk only.)

Besides the root cause the validator now stops the same junk from any provider: `MinutesText` rejects open questions and topics that
contain `]`, `}`, `{`, a code fence or `</`, a JSON key (`decisions: [`), "I will …" and "JSON" next to a word about the model's own reply
("generate", "final", "valid", "output", …; a meeting that really asks "should the export be JSON or CSV?" keeps its question), or
fewer than three letters or digits; it strips list markers (`- `, `* `, `•`, `1.`, `2)`) from topics and a stray `[S6]` tag from
questions, and removes repeats. Tests: `LanguageModelWhitespaceTests`, `LanguageModelRealJSONTests` (model-gated), `MinutesChecksTests`.

### B. Why items were dropped

`validateMinutes` now says why, with counts only (no transcript text): `ValidatedMinutes.drops` (`decision.quoteNotFound`,
`decision.wrongSegment`, `task.unknownSegment`, `entity.mentionNotInSegment`, …, `topic.junk`, `open_question.junk`), the number of due
dates the model wrote, the unreadable ones and the **raw violations of the due-date rule** (the meeting's day or the day after, nothing
in the segment that says so; the date is removed and the task stays). `MinutesDiagnostics` carries them to the debug log (`Logger`,
subsystem `local.vauta`, category `Minutes`, level debug) and to the `llm-eval` traces (`detail.checks`, `dueRuleViolations`,
`junkTopics`, `junkOpenQuestions`); the per-meeting result also keeps every reply of the run (public transcripts only).

**The 66% drop rate** (6 meetings, Gemma, 2026-10-13 code before the fixes below): 31 proposed, 11 kept, 20 dropped. 11 were entities
with `"id": null`: the schema let the model list names it could not link, and the app can only keep a mention of a person or project of
the list. 9 were quotes that failed the check: three were cited at the wrong segment (the words are in another segment), and the rest
did not match the cited segment: the quote joined the end of the previous segment with the start of this one ("Or maybe when you yeah.
It lights up all." against the segment "It lights up all."), or "corrected" the speech (a dropped "It" in "…realise that. It We have
short time"), or was a paraphrase. Those are real errors of the model and the quote check is what catches them: **the verification
stays as it is.** (The "quote must be a substring of the cited segment" automaton from the design was not built, because it would
turn the check into a formality: the model would quote whatever is in the segment it picked, true or not.) Two fixes of real causes: an
entity's `id` is no longer nullable in the schema, and the minutes and block prompts say what a quote is (one segment, as written,
repeats and "uh"s included, 4 to 15 words, `seg` is that segment's number). Same six meetings after: 22 proposed, 13 kept, 9 dropped
(2 mentions with an id outside the candidates, 7 quotes: 4 not found, 3 in another segment); a sample of six runs, so the quote rate (9 of about 20
before, 7 of about 20 after) is a direction, not a result. A citation fixed up by Swift ("the quote is in exactly one other segment: cite
that one") would recover most of the "wrong segment" drops; it is a loosening of the check and is not done. Due dates were rare: of 27 runs (12 Gemma, 15 Apple)
the models wrote 2, both unreadable, and 0 broke the due-date rule.

### C. Answers: `found`, claims, text

- **Schema** (all backends). `{"found", "answer", "claims": [{"text", "citations", "quote"}]}`, `found` first.
  Integrated model: the grammar enforces the conditional shape (`OutputSchema.tagged`): `found: true` needs at least one claim, every
  claim at least one citation, and a claim's sentence and quote cannot be empty (`OutputSchema.text`: a minimum of 3 and 8 bytes; the
  closing quote is not allowed before it, and a cap that fires inside a claim fills the minimum with dots); `found: false` has no claims.
  While a meeting records the answer is bounded to 700 bytes and three claims of 300 bytes, so a capped answer still has its claims; any
  other question has the full schema (3,000 bytes, up to 12 claims). Model server: a **flat** object (`found` boolean, `answer`,
  `claims` with any count) is sent as `response_format` (`json_schema`) when the profile takes one, properties **in declared order**
  (`OutputSchema.jsonSchemaData()` writes the text by hand and `ServerRequests` splices it into the body as written, after the
  `response_format` key). It is flat on purpose: a root-level `anyOf` is not understood by every structured-output backend, and the rule
  "found needs a claim" is checked by the app (below) and answered with one new request. A server that answers 400, 415 or 422 to the
  schema is asked once more without `response_format` (the prompt carries the same shape). Apple: the prompt and the validation.
- **What the app does with it** (`VautaPrompts.verifyAnswer`, `VerifiedAnswer.found`, `isUnverified`). The model's `found` decides.
  **`found: false` is a refusal and the model's own text is never shown** (nothing in it is cited): the app writes the refusal in the
  person's language ("I can't find that in your meetings."); what the model wrote under it is kept in `VerifiedAnswer.withheld` so that
  an evaluation can count a refusal that carries an answer (`refusedWithAnswer`) as its own bucket. **A reply with no `found` key** is
  an answer when it has a claim and is rejected when it has none (it cannot be told from an uncited answer). **Found needs a claim that
  cites something that was sent**: `found: true` with no claim, or only claims with no text or no in-range citation, throws
  `invalidResponse`. Apple and servers get one new request; if that fails too the error stands and nothing is shown as found. On the
  integrated model a claim with no quote is what the grammar writes when the cap fires inside it: if that leaves no claim, the finished
  sentence is kept as an unverified answer (`cutShort`) instead of an error. A found answer whose claims cite what was sent but all fail
  the quote check stays found and is shown as unverified (the existing "None of these points matched…" note), never as a refusal. In the
  evaluation `refused` is `found=false` without text of its own; a found answer whose claims all fail is "found but unverified".
- **Text.** `[S12]`, `[S5 · 01:18 · Others]`, `(S20:39)`, `[D2]` and times in brackets are removed from the answer and from the claims
  (`AnswerText.clean`; a bare `(D3)` or `(S3)` only when that code was among those sent, so "vitamin (D3)" keeps it); a model that writes back the old sample text ("a short answer", "<say you cannot find it in…>") gets an
  empty answer, which the app replaces by its own "I can't find that in your meetings."; the prompt no longer contains any sentence
  to copy (the shape is shown with empty strings), in all nine output languages and with or without documents (the prompt is English
  and names the language; a test runs the nine).
- **Prompt rules.** "Only what has been said up to now counts. If the answer may come later (…), do not answer with earlier material:
  found is false." "A proposal, a motion sent to a committee and a decision are different things: say it was decided, approved or agreed
  only if the material says so." And the quote rule of B for claims. A first wording ("say that it has not been said yet") made Apple's
  model answer "It has not been said yet." to 10 of 52 questions: the prompt never hands the model a sentence now.
- **What the rules do not do.** On the 10 questions whose answer comes later, three wordings of the time rule (the one shipped; a longer
  one saying the meeting is still going on; one that first checks that the thing was said) gave 5, 6 and 6 refusals out of 10, always
  the same four or five questions answered with earlier material (a designer's remarks before the formal presentation; a vote not yet
  taken); on the proposal-versus-decision questions Gemma now says "sent to committee" on some runs and "approved" on others. Prompting
  does not settle either; what would is another check (a second pass asking whether the quote answers the question) or a larger model
  on a server. Left open.
- **Time rule only while recording.** The rule "only what has been said up to now counts" is sent only when the question is about the
  meeting being recorded (`askInstruction(live:)`); a finished meeting, the library and documents get "The material is complete", so a
  question about plans ("what will be presented to the board?") is not refused by a rule meant for a meeting in progress.
- **Still open (2026-10-14): "the answer comes later" and proposal versus decision are not fixed in behaviour.** What was tried on 2026-10-13, on
  the real model (`llm-eval`, Gemma, 51 questions: the 10 "answer comes later", 3 proposal-versus-decision, 30 answerable, 8
  unanswerable):
  1. *Option 2, a time-aware filter on the cited segment, is vacuous for live answers*: the material of a live question ends at the
     moment of the question (the eval and the app both give the model the transcript up to then), so there is no later segment to
     drop. The failure is a different one: the model answers with earlier, related remarks.
  2. *Option 1, a second pass* (question, answer and the passages of its verified claims; "supported" true/false) was built and measured
     in two forms, then removed. As a bare verdict it said "supported" for 20 of 20 answers (the "later" set: still 5 of 10 answered,
     as before; the proposal question still "approved"). With a one-sentence reason written first it rejected 2 of 9: the proposal
     question (right) and an answerable fact question (wrong), and none of the "later" ones. It costs about 2.3 s per answer. A pass that
     takes away correct answers and no wrong ones is not shipped.
  What would settle it is a larger model on a server (option 3), or a decision to accept it (the person sees the note
  "unverified" only when no quote matches). The behavioural gate stays: the 10 "later" questions must be refused and the proposal set
  must not say "approved" for a motion sent to a committee; `llm-eval` reports both, no test pretends to cover them.

- **Re-run after 2026-10-13** (same 51 questions, Gemma only, asked while the meeting "records" as the app does, Mac under foreign load,
  load1 about 3 to 4; not comparable in time with the A/B). Answerable (33): found 33, refused 0 (the A/B counted 76 of 130 uncited
  answers as refusals), of which 17 with a verified claim and 16 found-but-unverified; no reply was rejected and no error. Not
  answerable (8): refused 8. "Later" (10): refused 5, answered 5 (3 with a verified claim, 2 unverified).

**Result** (52 questions of four meetings, the final code, both providers interleaved; 43 answerable, 9 not):

| | Apple | Gemma |
|---|---|---|
| Answerable: refused (`found` false) | 7 (16%; A/B 14%) | 0 (A/B: 0) |
| Answerable: found, at least one claim verified | 29 | 22 (51%; A/B: 31 of 130 had a verified claim and 76 had no claim) |
| Answerable: found, no claim verified (shown as unverified) | 5 | 21 |
| Not answerable: refused / answered | 7 / 2 | 6 / 3 |
| Answers with a segment tag or a time in the text (A/B: 7 of 158) | 0 | 0 |
| Answers that echo the prompt's sample text (A/B: 19 of 158 for Apple) | 0 | 0 |
| Calls that failed with invalid JSON (A/B: 11 of 158 for Apple) | 2 (after the retry) | 0 |
| Answers closed by the cap | n/a | 0 |

The 21 unverified Gemma answers are the live problem. Of its 72 claims, 36 verified; 17 quoted words that are verbatim in *another*
segment of the meeting than the one cited (the model wrote the wrong segment number, often far from the right one: 15 for 60, 23 for
97); 11 were near misses (every word is in the cited segment but not in that order or with words added); 8 were not in the meeting.
Pointing the 17 at the segment that holds the words would raise the verified share from 50% to 74%, with the same evidence trail;
it loosens what "cited" means, so it is **not done** (the same trade-off as the minutes' "wrong segment"
drops in B).

### D. Apple's minutes cut off at the length limit on meetings of 30 to 60 minutes

**Reproduced** on a 45-minute Spanish meeting (`cdm191218_b`, 21 model calls, failed after 312 s). What the calls show (`EvaluationCall` now
records the budget, the prompt estimate and the reply length of every call, also for a run that fails): 10 of the 20 block extracts hit
their 819-token limit and were split, and 6 of the last 8 calls before the final one hit it as well (the merge rounds, which nobody
checked: a cut-off extract, half a JSON object, went on to the next round); and the final request, with about 2,500 tokens of extracts in front of it,
had 1,228 tokens (30% of 4,096) to write the whole minutes again, with every decision and task and its quote. It wrote 4,609
characters (1,193 snapshots of 1,228) and stopped. There was no room to retry with a larger limit (a retry needs 25% more room than the
context has left), so the job failed with `outputTruncated`. A second meeting (`IS1009b`) happened to fit (final answer of 863 of 1,228 tokens) and finished at 250 s; the same meeting
had failed in the A/B: the failure depends on how long the model happens to write.

**Root causes.** (1) Output budget against the context: prompt and answer share 4,096 tokens, and the final request asked for an
answer as long as its own input. (2) Cut-off extracts and merges were passed on. (3) Further, found while fixing this: the block prompt
named the keys of an extract but not the shape of an item, so Apple's model wrote decisions and tasks as plain strings ("03:27 · Speaker 2
(remote): I think Pernilla should do it"), which cannot be checked: the nine runs of the A/B that finished kept 8 of 54 proposals, and a version of this fix that still
left the shape out kept 0 of the 10 it got in 15 runs.

**Fix** (small windows only; the large-window path is as before). (a) The block prompt shows the shape of the extract with items. (b)
No merge rounds: the final request reads a digest of the extracts (`MinutesDigest`: per block its summary, topics, up to three
decisions and four tasks as one line each and open questions, cut in steps until it fits what is left of the window, the summaries
last) and writes only the title, summary, topics and open questions (about 400 tokens, limit 900). (c) Swift carries the decisions, tasks and
mentions over from the extracts, without repeats, and `validateMinutes` checks them exactly as if the model had written them. (d) An
extract that is cut off and cannot be split is left out; a merge that is cut off keeps its group. (e) A final answer that is still cut off
fails the job, as before. Tests: `MinutesSmallWindowTests` (every request of a 260-segment meeting fits the window with its answer, the
final request is the digest and asks for four keys, the items arrive, a cut-off final answer fails the job, a cut-off extract
is not passed on, a large window is unchanged, the digest fits at any budget).

**Result** (the final code, Apple on this Mac, one run each, on 16 meetings of 30 to 60 minutes, 15 of which failed in the A/B): **16 of 16 finished** (the A/B: 9 of 39), median 96 s (p90 150 s; the A/B's finished runs: 260 s), 176 model calls of which 7
were cut off at their limit and split (the final request: none); 156 of 401 proposed items kept (the A/B: 8 of 54). Most of what was
dropped (146) are mentions with an entity id the model made up. An intermediate version of this fix had the final request cut off
in 1 of 4 runs (the title, summary, topics and questions of a very talkative answer ran past 1,286 tokens): the digest instruction now
caps the lists, and a final answer that is cut off after its first fields keeps them (`ModelOutput.closingTruncatedJSON`: closed at
its last complete element, never completed) instead of failing the job; one that is cut inside the title or the summary still fails.
One meeting (`cdm200625_a`) was declined by Apple's guardrail in an earlier run ("The model declined to answer", also one of the A/B's
30 failures) and finished in this one.

### E. Latency guard for live answers

A live answer (a question asked **while a meeting records**; `LLMService.recording`) on the integrated model has a cap. Questions asked
at any other time (after the meeting, across the library, over documents) have the full schema and `budget.askOutput`, and no clock. The cap: `LLMService.liveAnswerTokens` = 480 tokens and `liveAnswerSeconds` = 30 seconds of
decoding (the reading of the prompt does not count). It was 640 tokens and 40 seconds when the cut answers below were counted; how many
answers the current cap cuts is not measured here. Answers to questions Vauta hears in the meeting (the Live answers setting, `AutoAskRequest`)
have their own, smaller cap: `gemmaTokens` = 320 tokens and `gemmaSeconds` = 15 seconds. The generator checks the clock at every step; when it runs out it ends the
constrained value like a token limit does (the shortest valid ending, finish `length`), so the text is valid JSON and Ask does not ask
again with a larger limit (it does for the other providers). The schema of a live answer is bounded (700 bytes of answer, three claims of
300 bytes) so that a cut answer still has its claims. The kept prefix is as before (`reusePrefix` for a whole meeting). In the A/B 90% of
the answers took 454 tokens or fewer (22 tokens/s, so 20 s) and the longest 1,849 tokens (62 s); with the cap nothing is decoded for more than
640 tokens then, 480 now. The cap does **not** bound the reading of the prompt (prefill), so it is not a bound on the wall time of a question. A first value of 25 seconds closed 13 of 52 answers early on a Mac loaded by three model processes (10 tokens/s), so it was
raised: at the normal speed the token cap comes first, and the clock only matters when the Mac is slow. After that change 0 of 52
answers were cut (`finish length`). Test: `theTimeLimitOfADecodeClosesTheValueLikeTheTokenLimit` (tiny model).

**Wall time of a live question, with and without the warm prefix** (release build, Mac mini M2 that was not idle, load1 2.9 to
4.6; one recording of the public meeting `ES2004d`, five questions in a row, `llm-eval --tasks live-answer`, the transcript growing
between questions; `warmPrefix` is true for four of the five, which the earlier A/B runs never showed):

| Question | Prompt tokens (cached) | First token | Wall | Tokens out |
|---|---|---|---|---|
| 1, cold (5.4k tokens of transcript) | 5,407 (0) | 28.3 s | 34.1 s | 132 |
| 2, same transcript | 5,399 (4,971) | 2.9 s | 6.7 s | 93 |
| 3, transcript grown to 11.8k tokens | 11,773 (4,971) | 47.3 s | 54.6 s | 166 |
| 4, same transcript | 11,777 (11,344) | 3.1 s | 13.5 s | 238 |
| 5, same transcript | 11,770 (11,344) | 3.1 s | 4.7 s | 37 |

Reading: with the prefix kept, a question costs about 3 s to the first token and the decode (4.7 to 13.5 s in all). Without it, prefill
runs at about 190 tokens/s on this loaded Mac (28 s for 5.4k tokens, 47 s for the 6.4k new ones), so the first question of a recording
asked late in a long meeting, and the first one after the transcript grew by thousands of tokens (a long silence of the prefix), can
take 30 to 55 s before the first token; the 79 s seen in the A/B re-run was this plus a long decode. The 40 s clock does not apply to
that wait by design (a cut prefill would leave nothing to keep). Five questions are too few for a p90; the figures above are the whole
sample. Not done: a time budget for prefill (whether the first question of a long recording should show progress or
be capped is open), and measurement on an unloaded Mac.

### F. Evaluation tooling

- **Probe.** The A/B's "foreign" load included Vauta itself because the probe was never told which process to leave out. `probe.py`
  takes `--watch-name Vauta` (found again every second, since every `llm-eval` run is a new process) and always leaves out its own pid;
  the watched processes appear under `watched` with `own_cpu_pct` and `own_watts`. GPU utilisation cannot be split by process, so
  `foreign_gpu_util_pct` is the reading only while the process under test is idle (`own_cpu_pct` under 5). In the traces, `gpuUtilPct`
  was *not* broken: it is read before the run starts, when the model is idle, so it is 0 on a quiet Mac by construction; the 92.7% of
  the old aggregate was the model's own use counted as foreign. Each trace now also carries `gpuUtilRunMeanPct` and `gpuUtilRunMaxPct`
  (sampled every second during the run; it includes the model's own work). A second defect found on the way: free and compressed memory
  in the traces were always 0 (`(a + b) * page >> 20`: `>>` binds tighter than `*` in Swift); fixed and tested.
- **Energy.** `aggregate.py` reports, per run, the chip's GPU energy integrated from the probe's IOReport intervals (each interval counts
  for the part inside the run; the first, which has no start, is dropped; the part of a run the probe did not cover is taken at the average
  of what it saw), also net of the GPU's idle power, as the **primary** energy figure for GPU work, and writes `energy.json`. The
  per-process `ri_energy_nj` (CPU only, 2% of a Gemma job) stays as the secondary figure. Example, 12 live answers of one meeting on the
  integrated model: 128 J of GPU energy per answer (5.9 J own-process); Apple's model on the same questions: 0.7 J of GPU, 0.3 J own-process
  (its work is somewhere the counters do not see).
- **Embeddings were off in every earlier LLM evaluation.** The earlier runs of `llm-eval` (minutes, live answers, live questions) used `EvaluationProviders.embeddings() = .disabled`, so
  retrieval ran on keywords only; their numbers say nothing about the search model. The retrieval tasks (`--tasks retrieval`, `--search-model`) measure it apart, without a language model
  (results in [SEARCH_MODEL.md](SEARCH_MODEL.md#results-e1-to-e5-2026-10-18-independent-judge)).
- **Concurrency with the search model.** `Vauta embed-loop` (standalone) and `llm-eval --with-embeddings <transcript> [--embedding-purpose
  query|document]` (in the same process as the language model, so they share the gate) embed a public transcript in a loop and report
  batch latencies. The search model was installed for this through Vauta's own pinned downloader into the scratch store (547 MB in 31 s,
  hashes verified). First measurement (Gemma minutes of one 8.6k-token meeting, `ES2011d`, twice each; Apple's minutes of
another meeting ran at the same time on this Mac, so the absolute numbers carry that load, `load1` 2.3 to 4.8):

  | | Minutes wall time | Embedding batches during the run |
  |---|---|---|
  | alone | 94.9 s, 93.5 s | n/a |
  | with a loop of **query** embeddings (8 passages per batch) | 97.1 s, 93.5 s | 86 and 82 batches, median 0.9 and 1.1 s, p90 1.7 and 1.8 s, worst 3.7 and 3.9 s (the first includes loading the model), 0 errors |
  | with a loop of **document** embeddings (8 windows per batch) | 89.5 s, 87.3 s | one batch each, which **waited for the whole minutes run** (90.7 s and 88.5 s) |

  A question's embedding therefore waits at most a burst or a chunk of the running generation (the minutes do not slow down), and bulk
  indexing waits for a generation to end, as designed (`MLXWorkGate`: interactive, live, minutes, bulk). The process's peak footprint with both
  models resident was 3.8 to 3.9 GB (4.4 GB in the Gemma-only runs, whose prefill buffers are larger: the GO criterion is at most 6 GB).
  Not measured: both models loaded for hours, and a 16 GB Mac. GPU energy per minutes run was 930 to 995 J
  gross in these six runs (the chip's GPU channel, with Apple's job on the GPU part of the time; the idle-power baseline had one sample,
  so the "net" column of `energy.json` is not trustworthy here).
- **Also fixed in the traces:** calls of a run that failed are kept (they were lost), each call records `maxTokens`, `promptEstimate` and
  `outputCharacters`, and a run's result keeps every reply for the public sets.

## The interface, reading while recording, recall and guards (2026-10-14)

Measured on the Mac mini M2 (24 GB), release build, `nice -n 10`, another workload on the same Mac (load1 1.5 to 3.3, foreign CPU
20 to 33 %), integrated model only. Traces were kept locally and are not in the repository. **There was no blind judge in this
step**: the numbers below are mechanical (counts, time, prefix reuse). Faithfulness of the extra decisions and tasks, and of the
answers that the guards changed, was not graded; the judge criteria C1 and C3 of `eval/rubric` remain open.

### F1. Why a warm answer took 3.3 s, and what it takes now

The 2026-10-13 warm answer read 452 tokens of its prompt again each time: the answer rules were the last message, after the transcript. A
first attempt put the rules in the kept prefix after the transcript, and that measured the same: every new line of the transcript
moved the end of the transcript, so the rules (about 450 tokens, 2.5 s of reading) were read again with each question. The rules now
sit in the **second message, with the people, before the transcript**; they do not depend on the language of the question (that line is
in the question message), nor on whether the meeting is still recorded: the rule about the moment of the question (live: "only what has been said up to now
counts"; finished: "the material is complete") rides in the question message, so the prefix is the same one from the first tick to the minutes and to the questions after the meeting. Every task starts with the same two messages: minutes, live
notes, live answers, the checks and the reading ticks. 50 questions on 10 meetings, `--guard g1+g2 --warm` (the integrated model
has read the meeting up to three segments before the question, as a recording does):

| | cold, as measured on 2026-10-14 (passages, nothing kept; removed on 2026-10-15) | warm (prefix read while recording) |
|---|---|---|
| time to first token p50 / p90 | 13.5 s / 14.9 s | **1.78 s / 2.64 s** (2026-10-13 warm: 3.33 s) |
| wall p50 / p90 | 19.9 s / 26.7 s | 10.2 s / 17.5 s |
| new tokens read per question | 1,600 to 2,300 (passages) | 137 to 250 (the unread tail and the question) |

The target of 1.0 s was **not reached**: reading 200 tokens at 15,000 tokens of context takes 1.1 to 1.6 s, and a first token adds
about 0.4 s. It would need a shorter question message (the answer-language and quotation-mark lines are about 40 tokens of it; in the fixes of 2026-10-14 the quotation-mark and JSON-keys line, which does not depend on the language, moved into the kept rules, and re-measured below it changed nothing measurable).
**Superseded on 2026-10-15 (below):** the "cold" column above measured the excerpt fallback of 2026-10-14 (the best passages, at most
1,500 tokens, when reading the meeting would take more than 8 s, 15 s after the meeting). Blind run 4 showed that it cost quality; the
fallback was removed on 2026-10-15 (R1), so that column is not the shipped behaviour.

### F2. The inner quotation marks

The 2026-10-13 answers and minutes with `"` inside text ("the so-called "budget" line") broke the JSON string: the grammar closed the
string at the inner quote. Two fixes: the grammar refuses a closing quote straight after a space (`StrState.lastSpace`) unless there is no room left,
and the prompts say "Inside text, write quotation marks as « » or ' '". `AnswerText` and `MinutesText.cleanProse` remove what still
gets through (ranges like "(S3 to S43)", TeX `$\text{…}$`, the words "segment 12", a summary cut at a half sentence is counted in
`summary.unfinished`).

### Slots, the reading ticks and memory

Two kept prefixes: `.meeting` (people, rules and transcript so far; extended at its end, also by the minutes) and `.ask`
(a question's prompt; dropped after 300 s without a question, which is the engine's idle timeout and what no caller overrides, or when the memory warning comes).
Deleting a meeting, and Erase Meetings and Context, drop both slots and the pin at once (`LLMService.forgetKeptTranscripts`, `LanguageModelEngine.dropKeptTranscripts`). Budget 1.5 GiB for both, 1 GiB for the
meeting on a Mac with 17 GiB or less (768 MiB meeting cap). Priority of MLX work: `bulk < warm < minutes < live < interactive`. A reading tick is
preempted (`GenerationPreempted`) by a question or a live note and retried at the next tick, never blocks transcription, and waits
under `ThermalPolicy` heat (serious). Ticks: after 30 s of recording, then every 20 s with 600 new characters, or every 2 minutes with
any new text, every 3 minutes in Low Power Mode. A tick took 1.1 to 4.4 s on a 20-minute meeting (the first 3 to 9 s). When the
recording stops the prefix is pinned for the minutes (15 minutes at most) and goes back to the idle rules when they are written.

### Minutes: the arms (3 AMI dev meetings: ES2011d, IB4002, TS3004b)

Decisions plus tasks kept per meeting. **Shipped (after the fixes of 2026-10-14): the streaming layout only** (`MinutesArms.shipped = [.streamingLayout]`), because the meeting's kept prefix (reading while recording) needs it. A1 (the recall wording) and A3 (the second pass) are behind `llm-eval --arms a1|a3`: A1 failed the first recall gate (median 5 kept decisions and tasks, against 6) and neither was graded by a blind judge (C1, C3), so neither ships until it passes on the 9 development and 8 test meetings. **The streaming layout's effect on task owners (C2) was not measured**: it changes how speakers appear (the transcript lines say only Me or Others; the speaker list is in the last message). Keeping it is the trade-off for reading ahead, and it is an open decision, to be taken with the C2 numbers. A0 = the 2026-10-13 prompt; A1 = the recall wording; A2 = A1 with owner mapping; A3 = A1 + a second pass
per window of about 12 minutes or 3,000 tokens (own grammar with the segment ids of the window, at most 8 decisions and 8 tasks of each;
cap max(45 s, 0.6 of the first pass)).

| Arm | kept per meeting | median | wall | meetings with no decision |
|---|---|---|---|---|
| A0 | 0, 3, 3 | 3 | 75, 117, 140 s | 1 of 3 |

## Findings of blind run 4 (2026-10-15)

### R1. Cold questions answered from a starved excerpt (fixed)

**Finding.** In blind run 4, 80 of the 193 cold integrated questions (59 of the 156 the judge looked at) were answered from a prompt of
1,100 to 2,400 tokens instead of the whole visible transcript (median 8,242 in run 3), with nothing cached. Those scored 0.52 against 0.78
for the same questions in run 3 and 0.80 warm; the first token took 13.3 s (p50); 10 of Gemma's 12 false refusals were among them. The
pattern was always the same: the first question at a new place in the meeting got the excerpt, the next ones at that place got the whole
transcript from the cache (`cdm191218_a` q05: 1,938 tokens, 0 cached; q06 and q07: 9,690 tokens, 9,563 cached).

**Root cause.** Not a wait behind a background reading (the traces show `gateWaitSeconds` and `slotWaitSeconds` of 0.00 on every excerpt call:
the excerpt call runs at interactive priority on its own slot and nothing blocks it). It was the cold fallback of the first builds
(`LLMService.ask`): when the estimate of reading the kept-prefix gap (`estimatedReadSeconds`, tokens over the measured prefill speed, 150
tokens/s before one has been measured) was over 8 s live or 15 s after the meeting, the question was answered from the best passages and a
reading of the whole meeting was started in the background "for the next question". At the real speed of 140 to 200 tokens/s any
transcript over 1,500 to 3,000 tokens is over that limit, so every cold question fell back, and the background reading finished during
the answer's decoding, which is why the next question found the whole transcript cached. The excerpt itself still spent 10 to 13 s
reading its 2,000 tokens: the fallback was neither fast nor good.

**Fix.** The fallback is gone (`estimatedReadSeconds`, `coldFallbackLive`, `coldFallbackFinished` and `fallbackPassageTokens` are
deleted). A question about one meeting whose transcript fits the Ask window always sends the whole visible transcript. It uses the meeting's
kept prefix when that meeting is being read or was just recorded and the Ask prefix otherwise, so a reading of this meeting that is in
flight is *joined*: the reading steps aside at its next chunk (0.3 to 0.4 s, `GenerationPreempted`) and the question continues from what
was read, without reading anything twice. A reading of another meeting is not waited for (separate slot, interactive priority on the gate),
and the question no longer starts a second reading in its place. The reading shows its progress (`onPrefill`) and can be cancelled.
Past the window the passages path is unchanged. The window is `ContextBudget.askInput`: 20,000 tokens at a 32,768-token context, scaled by
the context, so **about 40,000 tokens** for the integrated model (65,536); on a small window it is what the context leaves after the answer. The warm path is the same code: its measured time to first token
on the first 12 questions of `EN2002a` with `--warm` was 1.76 s p50 (1.78 s on 2026-10-14).

**The price, stated plainly.** A cold question now waits for the reading of the part of the transcript that is not in the kept prefix: at
the measured 140 to 200 tokens/s that is about 20 s for 3,000 tokens and 40 s or more for 8,000. For a transcript near the window (about
40,000 tokens) it would be about 200 to 285 s to the first token; that figure, and "about 100 s" for 20,000 tokens, are **computed from the
prefill speed, not measured**. The time to first token of a cold question went **up**, not down. Cold is the normal case for a question about a
**past meeting**: any meeting other than the one recorded last, and any meeting after the Ask prefix was dropped (the idle timeout, a question
about another meeting, memory pressure) reads its whole transcript on the first question; the questions that follow at that meeting reuse the
prefix. It also happens for a meeting that was not read while it was recorded (the first question before the first tick, Low Power Mode, a hot
Mac, a meeting whose window was exceeded and is back under it). Only a meeting read as it was recorded and asked about right after answers in
the warm 1 to 2 s. The cold wait has no time limit, also while recording, where the reading holds the lane ahead of the live notes; whether to
limit was decided on 2026-10-15: **the wait has no time limit**. While it lasts the Ask card shows the model's reading (`Reading the meeting · N%`, from `onPrefill`; the generic "The model is reading your meetings" line shows before the first report); a test checks that a cold question reports the reading stage.

**Measurement** (release `llm-eval`, cold, `--quiet-wait 60`, integrated only, the 80 questions that got an excerpt in run 4. All 80 were
live answers (task `live-answer`, asked during a replayed recording with a partly read meeting prefix): **the after-meeting Ask path, where a

### R2. `found` true with a sentence that says "not specified" (fixed)

After the meeting, the integrated model sometimes wrote `found` true with an answer such as "El material no especifica cuántas personas
asistieron", and a claim to go with it. The prompt now has a rule for it (in the kept rules, so the prefix text changed once: "found is true only if
the material says the answer; an answer that says the material does not specify, mention or say it is a refusal: found is false; if the
material answers only a part, answer that part"; with the three-way `found` of the live guard it names "yes" and "no"), and `verifyAnswer`
checks it for every provider: if every sentence of the answer (at most four) only says the material (or nobody: "it is not specified", "no se menciona") does not state something, in English,
Spanish, French, German, Italian, Portuguese, Japanese, Korean or Chinese, and none of them joins it to something else ("although", "but",
"however", "only", a semicolon or a colon: "aunque no se especifica el monto, se mantuvo el presupuesto"), the answer is turned into the refusal
(`found` false, no claims, the app writes the sentence). A partial answer that also says what is missing stays an answer. The patterns are a
list of phrases, not a classifier: a sentence worded in a way it does not know stays as the model wrote it. A later fix narrowed them:
an ordinary negative fact said in the meeting ("the client did not give approval", "El presupuesto no incluye viajes", "María no sabe usar la
herramienta") is not an absence, so the patterns name the material as the subject or are impersonal ("is not specified", "no se menciona"). A
sentence with a speech verb and any subject ("the vendor did not mention a date") counts as an absence only when no claim of the answer was
verified: a quote that was found in the material wins. Tests cover negative yes/no answers with a verified quote in all nine languages.
**Final verification (2026-10-15):** the rule is now one line: the answer becomes a refusal only when **no claim verified** and the prose only declares absence (`declaresNothingFound` has no flag any more; `verifyAnswer` asks it only when `claims` has no verified one). With one verified claim a negative answer stays an answer whatever words it uses ("Nein, ein Termin ist nicht festgelegt", "The budget amount was not stated by the vendor"); `found` true with 0 of 2 claims verified and an absence sentence is a refusal.

### R3. Answers that stop mid-sentence, and length cut-offs that were not flagged (fixed)

- A length limit on the integrated model (finish reason `length`, including the loop guard and the time cap) now marks the answer as
  `cutShort` even when its claims were verified. Before, only the case "the only claim is filler" was flagged. A claim of filler next to a
  finished claim also flags it (it was dropped silently).
- A quote or a claim sentence that has no letter or digit ("........", "…") is filler and is never a citation, in the validation (the
  grammar's shortest valid ending for those fields is exactly that, so the grammar cannot be changed without making the cut answers invalid).
- A long answer that ends without closing punctuation is flagged only when it came within a tenth of the grammar's byte cap (450 of 500
  bytes live, 2,700 of 3,000 otherwise, measured on the whole answer and not on the 2,000 characters kept for display: before, a Latin-script after-meeting answer never reached 2,700 bytes once clipped): the grammar closes a string at its cap with finish reason `stop`, which is how a warm answer ended
  "...bien en". A shorter answer that ends on a figure, a percent sign or a list item finished and is not flagged. The text is not trimmed.
- `cutShort` with verified claims shows the claims as verified with one line under them (new string: "The answer reached its length limit, so
  its last sentence may be incomplete."; it says nothing about the quotes, because it also shows on a partly verified answer); with no claim at all it is
  still shown as cut short, not verified. Copy Answer and the exports carry the same line (`incompleteNote`).
  `VerifiedAnswer.kind` is `.cutShort` only in that second case.


## Decisions of 2026-10-15 and the last verification fixes

- **A. Apple's "must be a decision" filter is off by default.** `LLMService.decidedFilter` is false; `setDecidedFilter(true)` and `llm-eval --decided on` keep it available. The measurements above (39 of 78 decisions dropped, about as many true as false) are why.
- **B. The integrated model is idle while recording when "While recording" is Apple Intelligence.** `warmMeetingPrefix` returns before loading or reading when the live provider is not the integrated model, so nothing is read in the background and the model is not loaded until the recording ends; no prefix is pinned, and the minutes read the whole transcript cold (the meeting slot, as for any past meeting), which makes them slower to start. Settings → Models says so (the description under "While recording" and the Activity line, in the nine languages). If Apple Intelligence is not available the live work stays on the integrated model and it reads as before.
- **C. "Only related" answers keep the orange "Related" badge** with secondary text and no green seal (confirmed, unchanged).
- **D. Cold questions wait for the whole transcript read, with no time limit** (accepted). The Ask card shows the reading progress during the wait (see R1).
- **Deletion and failed calls.** The meeting that owns a kept prefix is recorded when the call that writes it starts (`LLMService.keeping`, around every Ask and minutes chat call), not when it succeeds, and again when it ends: an Ask or minutes call that wrote the prefix and then failed, threw (invalid reply, length cut) or was cancelled still lets the deletion, erase and retention drop it. The slots keep a set of meetings, because a slot holds one prefix at a time and a call that fails before writing leaves the previous one in place. A lookup of the meeting that fails (a cancelled task) no longer counts as "the meeting is gone".
- **Localized strings.** `scripts/check-strings.sh` flags a localized value that repeats a stretch of 16 or more characters right after itself or has the same sentence (12 or more characters) twice; it found and fixed the doubled length-limit note in ja and zh-Hans.

What it is: while a meeting records, Vauta notices questions asked aloud and shows a short, verified, cited answer card in the panel
(CHANGELOG, "Live answers"; code map in [ARCHITECTURE.md](ARCHITECTURE.md); privacy in [PRIVACY.md](../PRIVACY.md#live-answers)). This section says
what was **measured**, with which data and tools, and what was **not**. Everything below was run on the Mac mini M2 with 24 GB of the measurements
above, in a release build, on public transcripts, in a throwaway store, with no model server and no audio; the Mac was not idle (the traces record the load: `quiet` bucket, load1 1.9 to 3.6, one run with 28% foreign CPU), so absolute times are not clean.

### Status of the GO gates (2026-10-17): measured, and **not passed by any backend**

The labelled set now exists (built outside the repository and not part of it: 9,082 sentences, two label passes and an adjudication, **all of them separate model passes: no person has reviewed the labels**; Cohen's kappa for `kind` 0.79 in English
and 0.74 in Spanish; `answerable` kappa on the rows both passes called information is only 0.57, and the so_far recall and false-card gates depend on that field; the labels of the real-ASR condition C are not independent: pass B copied pass A's labels by alignment and A defaulted the rest to not_question; each question has an `answerable` value, a gold answer and gold segment ids; the real-ASR English condition C and the series' minutes
as documents were prepared; 50 sentences are ready for a human spot check, **not done yet**). What follows measures the code of this tree
against it, in the section "Evaluation of 2026-10-16" below. What is **still not done**:

- **The answers' text was graded by one blind judge (2026-10-17)**, one grader and no second pass, so no kappa for the card grades. The results are in "Blind judge of the cards (2026-10-17)" below. The rubric folder named for the judge was empty; the judge used `tools/llm-eval/rubric/LIVE_ANSWER_RUBRIC.md` and graded each shown card on its own.
- **No model server was measured** (the evaluation never contacts one). `LiveAnswerDefaults` says so for the server.
- The replay is on a simulated clock, with no audio and no concurrent transcription: **"no added dropped ASR chunks" is not measured**, and the energy figures are per
  replayed meeting-hour without idle time. Condition C (real Vauta ASR on the AMI audio) and the documents of the series were replayed in the 2026-10-17 run (below), also on a simulated clock. The energy and dropped-chunk figures of that run are in the same section.
- Accessibility: the manual VoiceOver and keyboard pass over the card is not done ([ACCESSIBILITY.md](ACCESSIBILITY.md)), and whether the real menu-bar panel stays
  non-key when an answer appears was not tested.

### Deviations from the design, and why

- **Standard sensitivity is 0.50, not 0.55.** The design says Standard accepts "punctuation alone" and gives the mark a weight of 0.50, which 0.55 would
  reject. With 0.50 a sentence with a question mark and at least four words is a candidate; interrogative plus inversion (0.60) too.
- **The Answers card is the first card of the panel's scrolling part**, before the live notes, and the transcript is a sibling of the scroll. (It was the first card at
  first, then the last: first it pushed Mark a Moment and the quick note out of view, then on a short screen (checked at 740 pt and on the 13-inch screen; at 640 pt and below the scrolling part has no room left) a new answer was below the fold with nothing to say it had
  arrived. The tools are now pinned or scroll as before, and the card takes room from the live notes.) Each of its rows is a stop of the scroll, so the viewport does not
  end in the middle of an answer. A new answer does not move the scroll (an earlier version scrolled to the card, which on a short screen hid Mark a Moment and the
  quick note and could move the quick note out of view while the person typed). A person who has scrolled down does not see an answer above; VoiceOver hears "Answer available".
- **A question being answered adds no row.** Only a small spinner next to the card's title (on a card that is already there), which stops the work when pressed,
  so the open answer never moves or grows while it is read.
- **The card budget is looked at before the answer is generated**: an answer that could not reach the card by the time it would be ready
  (`QuestionTiming.expectedAnswerSeconds`, 6 s, is the assumed duration; it is an assumption, not a measurement) is not generated and is stored as "Not shown".
  Turning the switch off, critical heat and serious heat also stop a model check that is already running: nothing is stored and no answer starts.
- **"Open in Ask" opens the Ask tab with the rewritten question and the stored verified answer with its citations**, as an answer of Ask; no model runs. A
  document citation opens its passage when the stored citation has the key, format and place.
- **The integrated model's token budgets are 160 for the check and 320 for the answer; the grammar caps the rewrite at 240 bytes (`QuestionCheck.maxQuestionBytes`: 160 Latin characters, about 80 in Japanese, Korean or Chinese, estimated not tokenised; cut rewrites are not counted in the replay output) (the Evaluation of 2026-10-16 ran with 128 for the check, 176 in the first replays; the 160 build was not replayed, so its check latency, timeouts and energy were not measured), not 96 and 260; Apple and the servers get 192 for the check** (96 cut 63 of Apple's replies in the first evaluation).  Original reasoning for the integrated model: Its grammar keeps 64 tokens back to close the
  JSON (`Generator.closeSlack`), so a budget of 96 allowed about 32 tokens of text: the first replay cut every one of 35 checks at 32 tokens (the rewrite
  of the question stopped mid-sentence), and 260 cut the one answer of the Spanish replay at its limit (196 tokens, no usable answer).
- **On the integrated model the past meetings' and documents' passages that follow the transcript are at most two passages within 2,400 characters
  and one document passage.** With three passages the first replay measured 13 to 15 s to the first token of those answers.
- The check's prompt is shorter than the design's (the six kinds are in one line, not four bullets).
- **The replay is one lane**, like the app's, and the queue time is measured from when a candidate settled (the app measures its 45 s from when the
  line arrived).
- **The first-run hint** is part of the Answers card at the first recording; it counts as seen once it was on screen or answered (a recording where it never reached the screen shows it again at the next one).
- `liveAnswersModelCheck` is a hidden preference without a control in Settings.

- **Spanish recall rests on one label**: the held-out Spanish meetings hold a single `so_far` question and the development meetings none, so the recall gate cannot be judged in Spanish.
- **No backend passes the gates.** Precision, `so_far` recall, false cards per hour and the latency of Gemma all fail on the held-out meetings; the correctness of the cards was not

- **The first fixes did what they were meant to mechanically and did not raise the precision.** Apple's cut replies fell from 41 to 12 checks; non-question
  rewrites are dropped; Spanish candidates are one clause of at most 160 characters; the opinion penalty is -0.40 (the 0.55 to 0.60 band no longer reaches the check); a Gemma

- **Energy** (replay, GPU energy of the whole chip from the IOReport counters, no idle time, Mac shared with other work at 23% to 29% CPU): Gemma used 2.09 Wh per replayed
  meeting-hour on `IB4010` (English, 48.9 min; gate <= 1: **fails**) and 0.55 on `cdm181025_a` (Spanish, 45 min); Apple's replays showed 0.01 and 0.00 Wh on the GPU counter (its model's

- Not done: warm-minutes first token with detection on and off. The switches exist (`--no-detection`, `--closing-probe`, see tools/llm-eval) and were not run.

The Spanish cells hold 3 to 7 cards and one so_far item, so their passes say little. In arm C the gold segment ids are manual-transcript ids, so those cards were graded against the gold answer and the visible ASR text. Document citations are not in the replay record, so the 4 cards labelled `document` could not have their source checked and were counted as not wrong. Three cards were counted correct although the gold says `later` because the answer was visible before the question.
- **Labels:** the labelled set is still two model passes and a model adjudication, with no human review; the spot check of the 50 sentences is pending.

### Answer language of live answers (2026-10-17)

The 13 English questions answered in Spanish all came from the integrated model's **check** (S5), not from the answer: the check rewrites the heard sentence so it stands alone, its prompt said only "in the language of the line" and carried Spanish examples, and Gemma often wrote the rewrite in Spanish (about 35% of the English rewrites: 39 of 107 in A, 43 of 156 with documents; Apple 3 of 1,136). The answer step then took the language of that rewrite. Apple's model was not affected in the replay. Minutes (language set on the meeting) and the person's own Ask (language of the question, else the meeting's) did not go through the rewrite, so they were not affected.

Fix: the check names the language of the line ("in English, the language of the marked line, without translating it"); a rewrite whose language differs from the sentence's is replaced by the sentence itself (every backend); the answer language comes from the words heard, then the rewrite, then the meeting's transcription language; and an automatic answer written in another language than the question is not shown.

Replay with the real Gemma 4 E4B (`llm-eval --tasks live-questions`, integrated, whole meetings, same sets; the language is judged by a stop-word count, which matched the blind judge's 13 before):

| | Before | After |
|---|---|---|
| English cards in the replayed A meetings (EN2002b, EN2002c, IB4010, IS1009d) | 7 English, 5 Spanish | 9 English, 0 Spanish |
| English cards with documents (7 meetings) | 10 English, 8 Spanish | 18 English, 0 Spanish |
| The 13 affected cases, answered again | 13 Spanish | 4 answered, all English; 9 no longer reach a card (no answer, answered aloud, timeout; the replay is not deterministic) |
| English rewrites in Spanish | 82 of 263 | 0 of 269 |
| Spanish control (6 cdm meetings, `--sensitivity high --keep-answered-aloud`) | 20 of 20 Spanish cards | 22 of 22 Spanish cards |

Limits: Gemma's answers vary from run to run, so the card counts are not a paired comparison; the 13 are not guaranteed to reappear. The language test is a word count, not a judge.

## Pre-meeting brief agenda: not shipped for this model

In the brief's blind evaluation (8 test series, synthetic fixtures; docs/BRIEF.md) the integrated Gemma 4 E4B wrote an agenda for 16 of 16 test briefs and its lines were well grounded (1.4% unsupported plus hallucinated on test, 0 hallucinated), but only 54.1% were judged useful against a gate of 70%, and the agenda did not change how prepared the judge felt. The agenda is therefore hidden for this model (`BriefAgendaShipping.shipped` is empty). No comparison with other products is claimed.

## Tasks, decisions and owners in the minutes (development phase)

The phase after the judged evaluation of the post-meeting actions: the stored tasks and decisions were too error-prone to put
in a follow-up email. Apple listed many non-tasks and non-decisions (chatter, ratings, fragments, items read from earlier minutes) and lost real
closing tasks; the integrated model (Gemma 4 E4B) listed few and named the wrong owner (the asker, or the user) in most meetings. Everything
below was built and tuned on the 34 DEV meetings only (the brief-phase series and the actions evaluation's development series); the test series,
their gold and the judge files were not opened. The DEV gold is one model pass over the transcripts with no human review and is not
exhaustive, so precision measured against it is a floor (see "Adjudication").

### What changed

- **`ItemEvidence`** (no model, both backends and servers; `Sources/VautaCore/LLM/ItemEvidence.swift`, word lists in `ItemCues.swift`, nine
  languages, English and Spanish measured). It reads the clause of the cited segment that carries the item and the lines around it (the previous
  one and up to three after it, stopping at a 90 s gap). It **drops** what is not an item: a recap of earlier minutes (a cue such as "last
  meeting" up to two clauses before, or past-tense "we decided" in the first 15% of the meeting), a rating without an agreement, meeting
  procedure ("go to the next slide", "I'll start off"), reported speech, something already done, text read out with no vote, a fragment (fewer
  than two words) and a repeat (content words, same segment or within two, across kinds; the task stays if it has an actor cue). It **keeps
  but marks `unconfirmed`** ("to be confirmed", out of the default email) a task nobody committed to (no "I'll", no request that was answered or
  addressed to somebody by name, no role charged), a hedged item, an unanswered question, and a decision with no agreement cue in the segment or
  the lines around it. Reasons are counted (`drops["task.recap"]`, `counts["decision.noAgreement"]`), never quoted; `llm-eval --extraction …,explain` adds one key per item for
  development. The filter runs after the quote check, so `dropped`, the citation counts and the verification rate are untouched.
- **`OwnerInference`** (`OwnerInference.swift`): the owner comes from the transcript, not from the model's label. In order: a person of the
  meeting named as the addressee or subject ("Ana, can you…", "Ana will…"); a self-commitment in the clause by a confident speaker; a request
  answered by another speaker who commits (certain) or only says "yes" (kept, **marked "owner not confirmed"**); a call for volunteers answered by
  somebody who commits; a role or third party ("the Industrial Designer will…", "que el ejecutivo…") or a group ("we should…"): nobody; anything else:
  the model's person only if the words name them, otherwise nobody (marked uncertain when the model named someone). The asker is never the owner;
  a doubtful label (low score, crosstalk) never gives a task; "Me" on a line that is not the user's is no proposal. Self-commitment is read inside the clause
  (a "?" or a "not" elsewhere in the turn no longer cancels it), and "I will need your snippets" is a request, not a commitment.
- **Closing pass**: one more request over the last 12% of the meeting or the last 6 minutes, whichever is longer, started at the beginning of the
  speaker turn and cut from the front to the room. Integrated model: the existing second-pass request on that one window, on the kept prefix
  (`MinutesArms.closingPass`, in `shipped`; `itemsPass` stays off), capped at the larger of 20 s and 30% of the first pass. Apple and servers on the
  map-reduce path: one request after the blocks, validated directly (not through the digest) and merged, earlier items winning on a duplicate; a meeting that
  fitted one request has none. It fails open.
- **Prompts**: definitions with exclusions, "Me" only when the transcript has a Me line, "due" only when the words say when, for the one-call
  minutes (integrated model, servers) and the closing request; the integrated model is asked for an owner only when the words name one (Swift decides the speaker).
  **Apple's block extract keeps its old wording**: the new wording with the cap of 3 decisions and 3 tasks per block was run and made things worse (below), and `blocks`/`uncapped` stay evaluation switches.
- **Due day**: stored only when the words in the segment and the next lines back it (`MinutesVerifier.dueIsInSegment`); a day the model worked out
  is dropped and the task stays ("next meeting" gives no day).
- **Evaluation harness**: the minutes files carry the flags the app stores and `ActionsEvaluation.seed` writes them through `applyMinutes`, so the judged email is
  the one the default settings draft (before, the harness dropped `unconfirmed` and `owner_uncertain`, so judged emails held items and owners the app leaves out);
  the follow-up detector is run per backend with its stored tasks and cited segments; a task owned by a speaker label is seeded with no owner, as in the app where nobody has named the speaker (`--actions-name-speakers` seeds the fixture's person instead, which assumes the user named every speaker); `--extraction`, `--meetings` and `minutes-replay` (above).
- Unchanged: the summary, title, topic and digest prompts, the quote check and re-anchoring, the storage schema, the email template. `ActionsRelease` was changed
  after the second judged run (detection on, the email draft held; see the end of this section). The app runs the new extraction on the integrated model only (`MinutesRelease.extraction(integrated:)`; see "Release state" below).

### The choice: what "to be confirmed" costs

79% of Apple's stored items and 57% of Gemma's are marked "to be confirmed" (out of the default email, shown with the mark in the minutes). Among the items that match a firm gold item, 63% (Apple) and 43% (Gemma) are marked.
Option (a), keep them marked (implemented, recommended: nothing true is lost from the minutes): email-grade 4.2 and 1.0 items per meeting. Option (b), drop them (`--extraction new,drop`): the minutes shrink to
4.3 and 1.1 items per meeting with the same precision, and half of the true items found disappear (Apple 0.63 to 0.31, Gemma 0.23 to 0.14 of the firm gold items). The code is the same switch.

### Limits

- The cue lists are phrase lists, not grammar. English and Spanish are measured on meetings; the other seven languages are covered by unit tests of each cue only. A missed cue marks an item "to be confirmed" or leaves it without an owner; it never invents one.
- The Spanish council meetings (ASR, noisy diarisation) give few email-grade items and the readings of the previous session's minutes are the main false positive; a voice-to-person mapping or a role mapping would be the next lever (a role such as "the Industrial Designer" is kept in the task text and gets no owner).
- The DEV gold is one pass of a model; the adjudication was model-assisted too. Gemma's rates rest on 35 email-grade items and 85 to 130 proposals.
- Apple refuses ("The model declined to answer") on one meeting in thirty-four in each of the three runs (the old and two new ones); that is not changed here.
- Not measured: the model server; a human reader. (The email and the follow-up detector on the new minutes were judged afterwards: see the end of this section.)

- *Citation-verification rate* (items that passed the quote, segment and entity checks over items checked, from the stored traces): Apple 0.571 old to 0.611 new (+0.041, 95% clustered bootstrap CI -0.035 to +0.115);
  integrated 0.921 to 0.912 (-0.008, CI -0.073 to +0.058). No drop is detectable; non-inferiority within 0.05 is not shown at this sample size.

**Switching the extraction on and meetings that already exist.** "Regenerate" (`applyMinutes`) deletes the open tasks and decisions the model wrote and adds back what the extraction in force keeps,
so regenerating an older meeting made with the integrated model before the switch can drop a task (a recap, a procedure, a fragment) or newly mark one "to be confirmed" or owner-uncertain. A task the person has acted on is not
among them: adding it to Reminders, ticking it, or editing it makes it theirs (`source = 'user'`), and a rewrite of the minutes keeps it with its ledger row (`ActionsStorageTests`). Decisions have
no such link and follow the model.

Fixes after the review of this phase (all inside the new extraction, so they apply where the app runs it: the integrated model): a recap is read in the clause that holds the quote and only when
that clause is not a request, a commitment or a role's task ("send the minutes of the meeting" is kept; "minutes of the", "the minutes from", 議事録 and "acta de la sesión" are no longer recap cues);
a procedure cue (slides, presentation, agenda) drops an item only when the item's own text has it and no agreement, role or request is present, and marks it "to be confirmed" when only the clause
around it has it; two tasks from one segment are one only when they overlap beyond their role words (an enumerated assignment keeps one task per role); a named person is the owner by "let/ask/tell" only
in the imperative ("Ask Ana to…"), never after "I'll", and a negated modal ("Ana can't…") hands nothing over; an agreement cue is read clause by clause, not in a question, a negation, "to be decided" or
"pendiente"; a hedged first-person commitment is kept with its owner and marked "to be confirmed" (a change from the design's exemption, which the judge's rubric did not accept). The speaker owner
of a plain "yes" is shown with the "not confirmed" mark.

Fixes after the second review (same rule: all inside the new extraction or behind it): a request whose first answer from somebody else refuses ("Sorry, I can't this week", "no puedo") has no owner and is "to be confirmed", also
when it named the person ("Ana, can you…"); a "yes" with a negation ("Yeah, no, I can't") is not a weak yes; a modal after a name hands the task over only when what follows it is about the item ("Ana will be away next week, so I'll send the deck" is the speaker's);
a request counts as answered only by a voice other than the asker's, and of two copies of a task the confirmed one stays; Korean, Japanese and Chinese "yes" words and the Spanish "si" count only at the start of the reply; the export
(Markdown, PDF, JSON) and the email input mark a speaker-label owner "not confirmed" like the screen does; the follow-up detector's task path skips days outside a year and tasks marked "to be confirmed" unless the passage they cite says that very day (the stored task does not say whether it was left out by the figures check or by the ranking of Apple's list); a meeting that fits one request with the old
wording but not with the new keeps the old wording for that request, so the new wording cannot move a meeting from the one-call path to blocks (counted as `prompt.oldWordingForFit`; how many meetings it concerns is not measured); the cue
cache is emptied when a minutes run ends. The replay of the 34 DEV meetings' stored replies after these changes moved the counts only slightly (Apple: 370 tasks both ways, 567 against 541 marked; integrated:
29 against 28 tasks, 52 against 55 marked); that comparison is not like for like (the replay has no closing request) and is not a measure of quality.

Fixes after the third review (same rule): a commitment counts as the answer to a request only when it is a bare acceptance ("I'll do that", "will do", "sure, I can", "me encargo", "lo hago") or when its
words are about the item (`ItemCues.answersRequest`), so "Can you look into the logo?" followed by somebody's "I'll send the minutes tonight" gives nobody the logo and does not confirm the task, in the owner rule
and in the filter alike; a question to a named person ("Ana, can you send the deck?") is confirmed only once somebody else says yes, silence or a change of topic leaves it "to be confirmed" (a directive,
"Ana, please send the deck by Friday", stays firm); "I have to", "I need to", "voy a", "tengo que", "je dois", "devo", "tenho que" and "preciso" commit only with an action verb after them (English, Spanish, French,
Italian, Portuguese; German puts the verb last, so its obligations stay weak cues), bare they are the weak `obligation` cue; a due day backed by the next lines does not mark the task "to be confirmed". Replay of the 34 DEV
meetings' stored replies with each change switched off in turn (same stored replies, no model; Apple, confirmed tasks): with the obligation phrases as before, precision of confirmed tasks 0.57 and 2.6 confirmed
tasks per meeting; with every committing line counted as an answer, 0.68 and 2.5; with both changes, 0.71 and 2.4; confirmed-task recall 0.20 in all three. The unanswered-question change moved no count, and the integrated model
moved by one task. Wrong owners among the 14 matched tasks with an owner: 1. The owner-accuracy fixtures
(`OwnerAccuracyEvalTests`) kept their published numbers after each request to a named person was given its recorded "yes". Not measured: how often real meetings leave a question to a named person without a spoken yes.

## Summary outcomes on a small window (phase "harness", H1)

**Problem.** On Apple's 4,096-token window a meeting of more than a few minutes is read in blocks and the summary is written from a digest of the block extracts (`MinutesDigest`). The digest has about 1,400 tokens
of room. It dropped the lines of decisions and tasks first and kept the process summaries ("the group discusses…"), so the summary read as a chronicle: in the 24 development meetings the shipped Apple summary stated about a
quarter of the gold decisions, and its prose carried "Me discussed…", the meeting's date, segment numbers and block numbers, and repeated sentences.

**Change (no new model call; behind `MinutesSummary`). In the app the integrated model runs `MinutesSummaryRelease.summary(integrated: true)`, which is `.shipped` (`outcomes`, `wording`, `checks`): the Swift summary checks on every meeting, and the outcome wording of the block extracts (`wording`) on a meeting long enough to be split into blocks of the 64K window (the reduce path); the outcomes-led digest (`outcomes`) is a small-window part and never reaches it. Apple's model keeps the legacy summary and digest (see "Harness phase: what ships"). The integrated summary gain comes from the H3 outcome rule and the items-first order plus these checks, not from the digest.**
- *Outcomes in the digest* (`outcomes`). The decisions and tasks of the block extracts go through the quote check and `ItemEvidence`, as the minutes' items do, but only to build a list for the digest: at most 12, ranked
  (confirmed decisions, confirmed tasks, then what is only proposed; the later of two equal ranks wins; a near-duplicate from another block is dropped), each with a status (agreed, rejected by a word list in six languages, task, "proposed only"). The list
  leads the digest. The blocks' own unchecked "Decided" and "Tasks" lines are left out. Under budget the narrative goes first: topics, then open questions, then the summaries of the earlier blocks before those of the last third of the
  blocks, and only then are the outcomes shortened (proposed first, then tasks, then the oldest). The digest rules ask for the results first, in order, with their final figures, a proposal written as a proposal, and no labels, block or segment numbers,
  speaker labels or meeting date. The block summaries lose segment numbers and the sentences that only say nothing was settled.
- *Wording* (`wording`). The block summary rule says what was decided, rejected or left open and the final figures, not what was discussed.
- *Checks* (`checks`, `SummaryChecks`). After the minutes are written, Swift removes a segment attribution ("según el segmento 23") from a sentence, drops a sentence that still names a segment, a block or the notes, or carries a date
  placeholder, drops a repeated sentence (word overlap of 0.8 or more), drops a sentence that has the user's channel label "Me" as its subject (English), writes "We agreed…" as "The group agreed…", removes the meeting's date unless the transcript says it, drops
  an open question that restates a decision or task, keeps at most 9 sentences, and counts the figures the transcript never says (`summary.figureNotInTranscript`; counted, not removed).
  Nothing is added; a summary the checks would empty is left as written.
- `llm-eval --summary old|new`, `--replay-live`, and the count keys `summary.*` and `timing.outcomesMs` (`--extraction …,explain` also records the digest).

**Measured on the 24 development meetings** (Apple, legacy extraction, `--summary old` and `--summary new` interleaved per meeting, same binary, load average 1.1 to 2.1 apart from one Spanish pair at 3.1 to 3.8; the sealed test meetings were not read):

## Apple's decisions and tasks: ranking and consolidation (phase "harness", H2)

**Problem.** Apple's model reads a long meeting in blocks and proposes decisions and tasks in every one of them. The list the app ships (the old extraction) has about 25 items per development meeting, of which 0.33 match an item of the

**Change (no new model call; behind `MinutesExtraction.ranking` and `.blockShape`, in the app for Apple's model: `MinutesRelease.ranked(integrated: false)` is true, see "Harness phase").**
- *Ranking* (`MinutesRanking`, Apple's model only; runs after `ItemEvidence`). Each item is scored from what the transcript shows: where in the meeting it falls (the largest term: the first stretch of a meeting is mostly talk about the topic), an agreement
  in the cited line or the next three, a commitment, a request or a group stating what it will do in the cited clause, how often the meeting comes back to its words within ten lines, a repeat from another block, a named owner, whether the
  checks found a commitment or an agreement, fewer than four words, and a word about running the meeting. Only the best items of the meeting stay firm (`limit`: 4 + minutes / 8, between 6 and 12); the others are kept and marked
  `unconfirmed` ("to be confirmed"). A question and an item whose figures the transcript does not back are never firm. A near copy of a later item (content-word overlap of 0.5 or more) is removed and the later one stays.
- *Block shape* (`blockShape`). The block extracts of a meeting that offers no person or project leave out `entities` (schema and shape in the prompt): the 211 entity proposals per 24 meetings that were all dropped as unknown are not written any more.
- `llm-eval --extraction new` (the default) now means the new extraction with both; `--extraction integrated` is the integrated model's `.shipped`; `rank`, `shape` and `procedure` (items about running the meeting are never firm; off in every shipped set: the development replay of 2026-10-24 lost a real firm item, so the condition was not met; see "Procedure items never firm") switch one part; `…,explain` records the features of every item

**Problem.** The integrated model proposes few items in its first reply (2.3 decisions and 1.8 tasks per development meeting against about 4.4 decisions and 4.4 tasks in the gold reading), so the firm recall of the list is 0.22 to

## Apple's Ask: question-aware rules, short windows, ordered passages (phase "harness", H4)

**Problem.** On Apple's 4,096-token window Ask answered about half of the answerable development questions with a citation on the gold line (live 90 of 182, after the meeting 92 of 202). Three causes were found.
(1) The prompt told every question that a proposal is not a decision ("say it was proposed or sent on"), and the model wrote that into answers about a figure or a name (29 of 84 fact, number and task answers after the meeting contain "propos…").
(2) Retrieval sent three keyword chunks of a hundred seconds (about 2,700 characters), and the gold line was among them only 63% (live) and 53% (after) of the time; `llm-eval` had never set the query translator, so a question in the other language than the transcript was searched untranslated (cross-language questions: 4 of 23 right).
(3) Across meetings the excerpts carried a title and a date, in score order, so "the first meeting" and "the last one" could not be counted.

**Change (no new model call; behind `AskHarness`, off in the app: `AskHarnessRelease.harness(integrated:)` is `legacy` for both backends; Apple's is a product decision).**
- *Rule* (`factRule`, Apple only). `AskHarness.isDecisionQuestion` is a word-stem cue (decide, agree, approve, vote, settle, resolve, choose, adopt, verdict and the Spanish stems); only a question that matches it gets the proposal rule. Any other gets "Answer with the facts the material states (names, figures, reasons, dates), as it states them." A miss costs the caution, never the answer.
- *Windows* (`windows`, Apple only, keyword ranking). `MeetingStore.retrieveWindows`: for each of the 40 best keyword hits (and the moments the user flagged) the lines from 20 s before to 40 s after, cut to 1,100 characters (the lines furthest from the hit go first); the score is the rank of the hits the window holds times (1 + 16 x the share of the question's ideas it holds); the 5 best windows that do not overlap are sent, within the same character budget as before. A question's number is searched in its other spellings (`AskHarness.numberVariants`: "12.50" also finds "twelve", "fifty", "half"; "twelve" also finds "12"; English and Spanish) and counts as one idea. A corpus that ranks by meaning keeps the chunks.
- *Order* (`order`, both backends). `VautaPrompts.passagesMessage(ordered:)`: passages oldest first; with two or more meetings each heading says "Meeting k of n" (the oldest and the most recent named) and the block says the oldest comes first. The place counts the meetings sent, not a series (the store has no series): "the third meeting" of a question is not "Meeting 3" of a label when the second was not sent.
- *Evaluation* (`llm-eval --ask old|new`). `new` includes the query translator (`translate`, evaluation only: the app always had it), `--tasks ask-retrieval` (retrieval alone, passages sent per question) and `sent` in the traces and answers, so retrieval recall is computed from the gold segments outside the app.

## Apple's notepad expansion: a reply that fits, is repaired and is salvaged (phase "harness", H5)

**Problem.** On Apple's 4,096-token window the user's shorthand notes were expanded for 43 of 120 attempts (live 22 of 90, manual 21 of 30 reached), and 196 of 464 requests ended "cut off at the length limit" (138 of 195 live, 58 of 90 manual). The notepad request is not guided on Apple (free text), so the causes were read from the raw replies of a first run: (1) the prompt shows `"text": "…"` and asks for "a verbatim quote" with no length, and the model copied whole segments (30 to 50 words) into each of 5 to 7 sentences, which ran past the 320-token limit; (2) the model copies the transcript's `[S10]` tag into `"seg": [S10]`, which is not JSON (the reply was dropped as "invalid JSON"); (3) a cut reply was thrown away although its first sentences were finished; (4) it writes "differs: true" or "seg: 101" at the end of a sentence's text.

**Change (no new model call; behind `NoteHarness`, off in the app, held: `NoteHarnessRelease.harness(integrated:)` is `legacy` for both backends; a large window never runs it).**
- *Prompt* (`prompt`). The quote is "a phrase of 4 to 15 words copied word for word from ONE cited segment", a sentence has at most 25 words, `"seg"` holds numbers (10, not S10), the shapes are empty (`"text": ""`, no "…" to copy); the tight grammar (a sentence at 500 bytes, a quote at 300, three sentences and three citations) applies only to a small-window backend that takes a grammar, which none of the measured ones does; Apple's note request is free text and a large window never runs this harness.
- *Budget* (`budget`). `ContextBudget.noteOutputLimit`: 700 tokens (the room the window leaves after the instruction and the transcript, at most 700, never under the old 320). The transcript window is unchanged (1,638 tokens).
- *Salvage* (`salvage`). A cut reply is closed at its last complete sentence (`ModelOutput.closingTruncatedJSON`, as Ask does), verified as any reply, and used when at least one sentence passes the checks; only a reply with none takes the old path (one larger try, then the failure). The larger try is salvaged too.
- *Repair* (`repair`). `NoteReply.repaired`: the `S` of segment tags outside strings is removed before the reply is read; `NoteReply.tidied`: a trailing "differs: true" or "seg: 101" is removed from a sentence's text.
- *Relevance* (`relevance`). `NoteReply.relevant`: a sentence of a note taken during the meeting stays only if its nearest cited line was said no more than 75 s before the note (or after it). (2) The blind comparison is done (see "Harness phase: what ships"): `MinutesQuestionsRelease` is on for Apple's model and held for the integrated one; the cap and the digest rule stay out. (3) The real-share metric is lexical; the blind judge of the sealed meetings (see "Harness phase: what ships") graded the lists by hand reading of the cited lines, and the integrated model's open questions were held.


## Live notes: empty shapes, copies, repeats, the owner "Me" and a reply that is repaired (phase "harness", H7)

**Problem.** Apple's live notes (every 2,100 characters or 3 minutes while recording) were mostly the transcript again: on the 24 development meetings (411 ticks) 30% of the decisions and 29% of the tasks were a cited line copied (over 0.8 of the words, over 40 characters), 101 decisions and 292 tasks repeated a note of an earlier tick, 98 tasks had the owner "Me" with no line from the user's own microphone, and 9% of the ticks failed with "invalid JSON". The prompt shows `"text": "…"` and `"owner": "Me | name | null"`, which the model copies; `validateLive` only checked that the segment exists. These notes also go to the minutes as hints.

**Change (no new model call; behind `LiveHarness`, in the app for Apple's model: `LiveHarnessRelease.harness(integrated: false)` is `.shipped`, see "Harness phase").**
- *Shape* (`shape`, Apple only). The instruction shows empty shapes (`"text": ""`, `"owner": null`, no "…" and no "Me | name | null"), asks for the notes in the model's own words, says what a decision and a task are, and says "Me" only for a line spoken by Me.
- *Copies* (`copies`). `LiveCheck.copiesItsLine`: a note whose content words are over 0.8 of those of its cited line (twice the shared over the sum), when it has over 40 characters, is dropped; so is a note with no letter or number in it.
- *Repeats* (`repeats`). `LiveCheck.repeatsEarlier`: a note of the same kind (point, decision, task) as an earlier note of the meeting (this reply's earlier notes included, the last 300 notes kept) is dropped when its normalised text is the same, or when 0.7 of the content words are shared and the two cite segments within 5 of each other.
- *Owners* (`owners`). A task's owner "Me" stays only when the cited segment is on the user's own microphone; "Me | name | null" is no owner.
- *Repair* (`repair`). A reply that is not JSON is read again in Swift: the `S` of segment tags is removed (`NoteReply.repaired`), and a reply cut at the limit is closed at its last finished note (`ModelOutput.closingTruncatedJSON`). A cut reply that can be read this way is used as it is: the larger second request is not made.
- *Which backend gets what* (`LiveHarness.shipped(integrated:)`, what `llm-eval --live new` runs, default): Apple every part; the integrated model `checks` (copies, repeats, owners, repair) with its request unchanged, because the same shape on it halved the points and left almost no decisions or tasks (below).
- *Evaluation*: `llm-eval --tasks live-notes --live old|new|checks|<list>`, same binary, `old` and `new` interleaved per meeting.

**Measured on the development meetings, Apple, 11 meetings (7 Spanish council sessions, 4 English), 231 ticks per arm, `old`/`new` interleaved per meeting.** Gold match is the lexical proxy of the diagnosis (cited line within 3 of a gold line, 0.15 overlap with the gold text); "unique" counts a note once.

## Harness phase: what ships (blind TEST, 2026-10-24)

Seven items of the phase (H1 to H7 above) were tuned on the development meetings only and judged once on the sealed test set: 20 meetings in 8 series, plus 4 cross-meeting series, 308 judged units, each graded blind as A/B with the arm order
randomised per unit (and per question or note inside Ask and notepad units). OLD is the app as it was, every switch off. NEW has every switch on. For Apple's minutes, OLD is the legacy extraction, summary and open questions and NEW the
ranked extraction with all switches; for the integrated model, OLD is the shipped minutes and NEW the items-first request, the new summary and the checked open questions.

**The judge** is a single LLM rater with no human review; the test gold was also model-assisted, and the judge was of the same model family that wrote the gold labels, so judge bias cannot be ruled out. There is no second rater and no agreement measure; a human spot check of the "product decision" and "ship" rows is
advisable. Grading leaned on the gold and the cited transcript lines (for the Spanish council meetings and parts of three English ones, not a full re-read of each transcript), so omissions the gold missed may be under-credited. An Ask answer that is right
but cites unsupportive lines counts as incorrect, and a live note cited more than three lines away counts as unfaithful; both arms were held to the same rule. Integrity checks passed before grading and again before unblinding (the 21 gold files, the 647
forms, templates and rubrics, the sealed key). The statistics script crashed after its checks and was run with one in-memory fix; the paired tests (exact two-sided sign tests on units, and a bootstrap of 5,000 resamples of the 8 series for a 95% interval of
NEW minus OLD) come from a second script on the same judgments. Switches were tested together: the effect of one switch alone, or of a subset, is not measured.

**Decision rule.** Ship: a significant gain (sign test p < .05, or an interval that excludes 0) and no significant regression in accuracy or safety (factual errors, unfaithful or invented content, refusals). Hold: no demonstrated gain, or a regression without a gain.
Product decision: both a significant gain and a significant regression, which is a product trade-off.

### Product decisions

**Off in the app** (each is a gain against a measured cost in accuracy or safety, or has no measurement of its own):

1. **Apple's summary (outcome-first). Decided 2026-10-24: keep the legacy summary; it stays off.** Gain: 46 outcomes covered against 27 (p=.023). Cost: factual errors 50 against 22 (p=.007), and the summaries are preferred 8 to 9. The ranked extraction
   (which ships) does not depend on the new summary. It could be revisited when Apple's extracts are cleaner (the errors are mostly outcomes misread from a noisy extract, see H1).
2. **Apple's Ask harness (question-aware rule, short windows, ordered passages). Decided 2026-10-24: stays off in the app; the comparison was re-run and judged blind, the result is below; it can be turned on later once a new run meets the judge's condition.** The recommendation of the judge is to hold. The OLD arm ran without the query translator that the app always has, and `--ask new` includes it (`queryTranslation`, evaluation only), so part of the gain belongs to the app's baseline, not to the harness: on DEV the translator alone raised the retrieval of the gold line from 0.626 to 0.698 (live) and from 0.530 to 0.579 (after the meeting) (H4). Gain as measured, harness plus translator: correct answers +11 points live (.588 against .481, p=.050) and +17 points after the meeting (.581 against .413, p=.0006). Cost: abstention on unanswerable live
   questions falls from .973 to .865 (CI excludes 0), and invented answers rise from 0 to 6 live (197 live questions) and from 1 to 3 after the meeting. Before weighing them: a bug in the number spellings of the short windows (a spelled number never found its digits, and the other way round; `retrieveWindows` took the words of the question's groups through a cast that always failed) is fixed, and the windows of the judged TEST build did not have the fix; the TEST comparison was re-run on 2026-10-24 with the translator in both arms (`--ask translate` against `--ask rule,windows,order,translate`, Apple only, 20 meetings live and after, 4 series cross-meeting, 407 questions) and judged blind by one LLM rater with no human review (44 units, 814 answers; every answer graded as invented was checked by hand against the transcript; report `judge-ask`, judgments hashed before the key was opened). Results, new against old, live and after pooled: correct answers among answerable questions 217 of 331 (65.6%) against 164 (49.5%), +16.0 points (CI +9.3 to +21.1, p=1.6e-6), most of it after the meeting (+24.3 points; live +7.0, CI includes 0); refusals of unanswerable questions 50 of 63 (79.4%) against 55 (87.3%); **invented answers 76 of 394 (19.3%) against 48 (12.2%), +7.1 points (CI +1.3 to +14.9, p=.005)**, doubling live (32 against 16, CI +3.4 to +13.0), with the high-severity ones up from 25 to 39. **On in the app** (they ship by the judge's defaults and are product choices that can be revisited):

4. **How many items stay firm on Apple, and what the rest looks like.** `MinutesRanking.limit` (6 to 12 by length) is a product choice (H2). Every item outside the limit is stored as "Unconfirmed" and left out of the default follow-up email: about 60% of Apple's list on the development meetings. The mark's help text used to say that a name, date or figure does not match the cited passage, which was false for an item that only did not rank; it now says only that the item is not confirmed in the transcript (9 languages), which is true for both. The reason is stored (migration 29, `decisions.unconfirmed_reason` and `tasks.unconfirmed_reason`, a short internal code and never meeting text) as `rank` for an item that did not rank and that no check had doubted, as `rank:<code>` (for example `rank:noAgreement`) for one that did not rank and that the evidence check had doubted softly (`tentative`, `noAgreement`, `noCommitment`, `procedure`: the ranking shows such an item as settled when it ranks inside the limit, so the doubt says nothing more than that it did not rank), and as `figures` or `question` for an item whose figures the passage does not back or that is a question (never settled, whatever its rank, so they stay in the main list with the "Unconfirmed" mark); rows stored before migration 29 have no reason and keep today's look (an old unconfirmed item is shown as doubted). **Decided 2026-10-24 and built: the ranked-out items are shown apart, in a group named "Other possible items" (nine languages) that starts collapsed.** In the meeting's Minutes tab it follows the Decisions, shows the count, and holds the ranked-out decisions and the ranked-out open tasks in the order of the meeting; each row keeps its time (it opens the transcript at that moment), **Mark as Checked** (the item becomes the user's and moves to the main list), delete, and for a task **Edit in Tasks**. Only a question, an item with unbacked figures, or one stored before the reason existed stays in the main list with the "Unconfirmed" mark and its help text. Measured on a no-model replay of the stored Apple replies of the 24 development meetings (`minutes-replay`, `--extraction new`, 2026-10-24): 581 items, 365 unconfirmed, **329 ranked out, 56.6% of the list or 13.7 per meeting (140 decisions and 189 tasks, of which only the open ones show in the group), 90% of the unconfirmed ones**; 1.5 per meeting stay in the main list as doubted (31 questions and 5 unbacked figures). Before this was fixed the ranking stored `rank` only for items the evidence check had not doubted: 17 items (2.9% of the list). The tab shows the group's open tasks but has no tasks section of its own (the firm tasks are in the Tasks tab, where a ranked-out task shows the "Unconfirmed" mark like a doubted one); whether to keep tasks in the group is open. The group never shows for a meeting with nothing ranked out, opens collapsed for every meeting, and VoiceOver reads the title with the count ("Other possible items, 4 items", plural in each language) and a hint; it is a standard disclosure control. Not checked with VoiceOver or with Full Keyboard Access on a real session. What each surface does with the group, because the items stay `unconfirmed` in the store: the **Tasks tab and Tasks mode** list a ranked-out task as today, with the "Unconfirmed" mark; the **Markdown, PDF and JSON exports** list the items in their lists with the same mark and `unconfirmed: true` (nothing is removed, and the JSON has no new key); the **follow-up email** leaves them out unless "Include unconfirmed items" is on, then marks them "to confirm"; the **follow-up detector** treats them like any unconfirmed task; the **pre-meeting brief** shows them with the mark. The ranking also keeps an item that the evidence check found hedged, without an agreement, without a commitment (a task nobody took) or about running the meeting ("go to the next slide") as settled when it ranks inside the limit (only questions and unbacked figures are never settled), which the earlier "to be confirmed" marking did not do (proposals stated as firm still fell from 50 to 20). The limit has a floor of 6, so on a short meeting nearly every item that is not a question and has no unbacked figure is shown settled and goes into the default follow-up email. **Decided 2026-10-24: procedure items are never firm if a `minutes-replay` on the development meetings shows no loss of real firm items.** The switch exists (`MinutesExtraction.procedureNeverFirm`, `--extraction ...,procedure`; an item whose text carries a running-the-meeting cue goes to the group with the reason `rank` or `rank:procedure` and does not take one of the firm places; unit-tested in `MinutesRankingTests`) and stays off in every shipped set: the replay was run on the development meetings on 2026-10-24 and did not meet the condition (see "Procedure items never firm" above: one real gold decision left the firm list in one of three passes, and two of five demotions were right). The follow-up detector no longer skips an "Unconfirmed" task whose cited passage says its due day in a clause that neither asks nor hedges; this applies to the integrated model too (where "Unconfirmed" means the evidence check found the task a question, hedged or uncommitted), and it was re-measured with `--tasks actions` on both backends on 2026-10-24 (see "DEV check of the shipped combinations").
5. **Apple's extraction switch itself** (the ranked extraction replaces the old one: same recall, a list 64% shorter, proposals stated as firm 50 to 20).
6. **Apple's live notes** become mostly points, 2.9 times the volume, and a note restated with a new detail within 5 segments can be dropped as a repeat (H7).
7. **Open questions on Apple** (H6; very short real questions such as "Who pays?" are dropped by the 4-word rule, and the `short` switch that would keep them awaits a DEV check): the form, copy, topic, settled, repeat and generic checks are on; the cap of three and the digest rule are out, so a list of about two per meeting is not what ships.

### Reproduce

Development and test sets are the public transcripts named in the sections above (the test set stays sealed in the maintainer's evaluation archive). Each unit runs OLD and NEW back to back, in alternating order, on one binary:

```sh
# minutes, Apple (old = legacy extraction, summary and open questions)
Vauta llm-eval --tasks minutes --providers apple --extraction old --summary old --open-questions old --sets <transcripts> --meetings <id> --out <dir>
Vauta llm-eval --tasks minutes --providers apple --extraction new --summary new --open-questions new --sets <transcripts> --meetings <id> --out <dir>
# minutes, integrated
Vauta llm-eval --tasks minutes --providers integrated --extraction integrated --summary old --harness old --open-questions old --sets <transcripts> --meetings <id> --out <dir>
Vauta llm-eval --tasks minutes --providers integrated --extraction integrated --summary new --harness new --open-questions new --sets <transcripts> --meetings <id> --out <dir>
# Ask (live and after the meeting), live notes, notepad, cross-meeting Ask: --ask old|new, --live old|new, --notes old|new
Vauta llm-eval --tasks live-answer --providers apple,integrated --ask old|new --warm [--after-meeting] --sets <transcripts> --questions <questions.jsonl> --only <id> --out <dir>
Vauta llm-eval --tasks live-notes --providers apple,integrated --live old|new --sets <transcripts> --meetings <id> --out <dir>
Vauta llm-eval --tasks notepad --providers apple --notes old|new --sets <transcripts> --notepad <notepad.jsonl> --meetings <id> --out <dir>
Vauta llm-eval --tasks ask-cross --providers apple,integrated --ask old|new --sets <transcripts> --cross-questions <ask_cross.jsonl> --only <series> --out <dir>
```

To measure the combination the app ships (not every switch on), per backend: `--extraction release --summary release --harness release --open-questions release` (any of the four flags set to `release` makes every backend run the `MinutesRelease`, `MinutesSummaryRelease`, `MinutesHarnessRelease` and `MinutesQuestionsRelease` choices for itself). To measure the never-firm procedure items against the shipped ranking, on the stored replies of the development meetings and with no model: `--tasks minutes-replay --replay-from <folder> --extraction new` against `--extraction new,procedure` (Apple's ranking; add `--extraction new,procedure,explain` to list each item's verdict). To separate Ask's translator from the harness: `--ask translate` against `--ask rule,windows,order,translate`.

The development tables of each item (H1 to H7) are in the sections above; they were measured on the 24 development meetings with the same commands, interleaved per meeting, and none of the sealed meetings was read while tuning.

## Links check per backend

The optional check of link pairs (Apple's model, the integrated model; never a model server) is off on every backend (`LinksRelease.modelCheck`). Packing: Apple's 4K window takes pairs greedily (each text at most 120 tokens, 300 reserved for the reply), the integrated model at most 20 pairs, only if already loaded and on the charger. **Judged 2026-10-25 (test series, one blind judge): the check is not used on either backend.** On Apple's model, vector + check (LSA) cut the seeded valid links from 9 to 1 and added a wrong "changes"; on the integrated model, vector + check (LSG) dropped its only natural true link (natural recall 0.12 to 0) and labelled a carry-over as a change (G8 fails on both; figures in [BENCHMARKS.md](BENCHMARKS.md#post-meeting-actions-part-b-links)). The integrated check used 0.028 Wh over 52 meetings (3 calls); that is not a per-meeting figure. **The keyword arms with a check (LKA, LKG) are not a measurement:** in that run the check only ran after the vector pass, so with no search model it never ran (0 model calls) and the "same set as LK0" result says nothing about it. The code now runs the check after the keyword pass too, in the `embed` job that holds the model's lane (same charger and quiet-Mac rules); that has not been measured. A pass that had to wait keeps its check and runs it when the job is queued again.
